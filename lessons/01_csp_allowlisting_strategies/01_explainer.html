00 — Which Modules This Spans

Builds on: Module 5: Nonce-Based Scripts Module 6: Hash-Based Scripts Module 7: strict-dynamic Propagation

Each of those three modules proved ONE mechanism works, in isolation, with its own server and its own proofs. None of them, individually, is the right place to answer the question a real team actually has to answer: which one should we use, and why? That comparison belongs here, not bolted onto any single module.

01 — The Big Analogy

Three different ways to prove someone's allowed backstage at a concert. A nonce is a wristband printed at the door, tonight only — perfect for content that's freshly generated on every single visit, useless if you need to hand out passes in advance. A hash is a laminated card matching an exact, pre-approved photo — perfect for a fixed guest list that never changes, worthless the moment someone's hair changes even slightly. strict-dynamic isn't a credential at all — it's "anyone person X personally vouches for and walks in themselves is in," which solves a problem neither wristbands nor laminated cards solve well: an unpredictable, runtime-determined chain of trust.

04 — The Code, Compared

Same problem — allowlist ONE inline script — three different mechanisms, drawn from the actual verified modules:

// Module 5: nonce — server generates it fresh
const nonce = crypto.randomBytes(16).toString('base64');
const policy = \`script-src 'self' 'nonce-\${nonce}'\`;

// Module 6: hash — computed once from fixed content, same every time
const hash = crypto.createHash('sha256').update(ALLOWED_SCRIPT, 'utf8').digest('base64');
const policy = \`script-src 'self' 'sha256-\${hash}'\`;

// Module 7: strict-dynamic — trust propagates from a nonce root
const policy = \`script-src 'nonce-\${nonce}' 'strict-dynamic'\`;
// (a script the root creates via createElement+appendChild inherits trust,
//  with NO nonce/hash of its own)

05 — Operational Tradeoffs (Beyond What Any One Module Tested)

⚠ Nonces cost you

  • Every response must be dynamically rendered — no full-page HTTP caching of the HTML itself
  • Requires server-side templating wired into every response that needs an inline script

⚠ Hashes cost you

  • A build step to recompute hashes whenever the script content changes — miss one and the deployment breaks silently
  • Doesn't scale to many distinct inline scripts — each needs its own hash entry

strict-dynamic avoids both costs for the scripts it covers, but only shifts the trust question one level up: you still need ONE nonce or hash to establish the root of trust in the first place — it doesn't eliminate the choice above, it extends whichever one you picked.
