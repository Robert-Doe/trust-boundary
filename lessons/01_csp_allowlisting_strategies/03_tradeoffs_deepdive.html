Scope note Like this cluster's history page, this is contextual/operational guidance, not a claim verified by a server in this course. The underlying mechanics (nonce timing, hash determinism, strict-dynamic propagation) ARE verified — Modules 5–7 — this page reasons about their consequences at production scale, which no single module's demo attempts.

The caching cost nonces impose, concretely

A CDN or reverse-proxy cache typically keys cached responses by URL, and serves the identical cached body to every visitor. A nonce embedded in the HTML breaks that model outright: if the nonce is baked into a cached response, every visitor gets the SAME nonce — which Module 5's Proof D showed is exactly the failure mode that makes a nonce meaningless (a reused nonce is not a nonce). Sites that need both full-page HTTP caching AND nonce-based CSP generally solve this with edge-side dynamic substitution (inserting a fresh nonce into an otherwise-cached response at the CDN layer) — real, but real infrastructure complexity Module 5's single-server demo never had to contend with.

The build-pipeline cost hashes impose, concretely

A hash is only as good as the last time it was recomputed. In a real build pipeline, that means: every time a template containing a hashed inline script changes — even a whitespace-only reformat, as Module 6's DECISIONS.md demonstrated — the deployed hash must be regenerated and redeployed together with the new content, atomically. A CI step that forgets this (or a template change that ships slightly out of sync with a separately-cached CSP header) reproduces Module 6's Proof B: legitimate content silently blocked, indistinguishable at a glance from an actual attack being stopped.

Why most large, JS-heavy sites converge on nonce + strict-dynamic

Given the two costs above, a common real-world shape emerges: use a nonce (accepting the caching complexity) for the ONE entry-point bootstrap script, then lean on 'strict-dynamic' so that script's own bundler-driven loading of everything else needs no further per-script credentials at all — sidestepping hash's build-pipeline fragility for the bulk of an application's script surface, while confining nonce's caching cost to a single, small, root script. This isn't a rule CSP enforces — it's an emergent pattern from the tradeoffs above, worth recognizing when you see it in a real site's headers.

What none of these mechanisms solve

All three are about controlling WHICH scripts can run. None of them address a completely different problem this course's Track 2 exists for: scripts that were never "loaded" from anywhere at all, because they arrived as a string handed directly to innerHTML or eval. That's not a gap in nonce/hash/strict-dynamic design — it's a different attack surface entirely, which is why Track 2 exists as a separate applied layer rather than a fourth CSP allowlisting keyword. See the CSP/Trusted Types layering cluster for that boundary made explicit.
