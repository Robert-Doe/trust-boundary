No single module states, end to end, exactly where CSP's job stops and Trusted Types' job starts. Module 14 came closest, but its scope was narrowly "does script-src cover this one gap" — this cluster is the place to state the full boundary precisely, using evidence pulled from across both tracks.

01 — The Big Analogy

CSP's script-src is airport security screening luggage AS IT BOARDS the plane — it inspects what's about to run and can refuse specific dangerous items (a script from an untrusted origin, an inline handler with no nonce). Trusted Types is the manufacturer requiring every suitcase to be a SPECIFIC APPROVED MODEL before it's even allowed into the terminal at all — regardless of what's packed inside it. Screening is powerful but reactive (it inspects contents); the manufacturing requirement is preventative but narrow (it only governs the suitcase itself, not what happens once the exact-right-model suitcase is on the plane). Neither replaces the other; a well-run airport has both.

02 — The Boundary, Stated Precisely

QuestionCSP script-src answers itTrusted Types answers it
Can this <script src> load from this origin?Yes — this is its core jobNo opinion
Can this inline <script> block execute?Yes — via nonce/hash/'unsafe-inline'No opinion (governs the ASSIGNMENT that PUT it there, if via a sink)
Can this onerror="" handler, injected via innerHTML, fire?Yes — verified in Module 14, script-src-attr covers itN/A — never reaches this point if guarded
Can this innerHTML assignment happen AT ALL, regardless of content?No opinion — Module 14's central findingYes — this is its core job
Can non-executing HTML (a phishing banner, a fake login form) be injected?No opinion, everYes — blocked at assignment, regardless of danger
Can this page be framed by another origin?Yes — frame-ancestorsNo opinion
Can this form submit to an untrusted origin?Yes — form-actionNo opinion

04 — The Evidence, Pulled From Across Both Tracks

Module 14 proved CSP's blind spot, under the strictest reasonable script-src:

// Module 14, Proof B — zero script, zero handlers:
target.innerHTML = '<div class="fake-alert">...<a href="http://evil.example">...</a></div>';
// → innerHTML assignment completed with ZERO errors, ZERO CSP involvement

Module 15 proved Trusted Types closes exactly that gap, and ONLY that gap:

// Module 15 — the SAME payload shape, now with require-trusted-types-for:
// THREW: TypeError: ... This document requires 'TrustedHTML' assignment.
// (identical error for dangerous AND harmless content — a categorical block)

Module 24 proved the two layers coexist in one real policy without conflict:

script-src 'self' 'nonce-...'; require-trusted-types-for 'script'; trusted-types dompurify dompurify-policy
// ^ one header, one policy string — CSP directives and Trusted Types
//   directives are just more entries in the same list

05 — What Neither Layer Covers

✗ NEITHER covers

  • Reading `document.cookie` or making arbitrary `fetch()` calls once script is already running legitimately
  • Server-side vulnerabilities (SQL injection, auth bypass) — this entire course is browser-side enforcement
  • A user being socially engineered into typing their own password into a convincing fake form THEY navigated to directly (not injected)

✓ Together they cover

  • Script execution from untrusted origins/inline sources (CSP)
  • Structural page hijacking: clickjacking, form hijacking, base-tag hijacking (CSP)
  • Any raw string reaching a dangerous DOM sink, executable or not (Trusted Types)
