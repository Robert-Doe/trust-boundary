This is the cluster that answers, directly and completely, the question this whole second track exists partly to answer: how does Trusted Types relate to prototypal inheritance? The prerequisites page set up the mechanism; Modules 22–23 tested it against real forgery attempts; this page is where the full answer gets stated in one place, with the deep-dives providing the "why does JavaScript work this way at all" context no single module's code motivates.

01 — The Big Analogy, Completed

Recall the RFID-badge analogy from Module 22: instanceof is a visual/paperwork check (spoofable), the sink's real check is an embedded chip a reader queries directly (not spoofable via paperwork). Here's the piece that completes the picture: prototypal inheritance IS the paperwork system. It's real, useful, and load-bearing for almost everything else in JavaScript — every array method, every string method, every object method you've ever called relies on prototype-chain lookup working correctly. Trusted Types doesn't distrust prototypal inheritance as a mechanism; it simply declines to use it for the ONE decision where "can this specific piece of paperwork be forged by the person presenting it" matters more than "is this convenient and how JS normally works."

02 — The Full Chain of Reasoning, Assembled

  1. Prerequisite fact: instanceof is purely a prototype-chain walk — it asks "does X.prototype appear anywhere in this object's chain," nothing more.
  2. Prerequisite fact: Object.create(X.prototype) lets ANY code construct an object whose chain contains X.prototype, with zero involvement from X's own constructor logic.
  3. Consequence: any security check written as if (x instanceof TrustedHTML) { /* treat as safe */ } would be trivially defeatable by exactly this construction.
  4. Module 16's fact: a real TrustedHTML is produced by a policy's createHTML method — a real, specific code path, not just "any object with the right prototype."
  5. Module 22's finding: the browser's REAL sink guard is not, in fact, written as instanceof — a forged object that passes instanceof TrustedHTML is still rejected, with a categorically different error ("Illegal invocation" vs. "requires TrustedHTML assignment").
  6. Module 23's finding: that resistance holds even against prototype pollution, reassigning the global TrustedHTML identifier, using a different prototype-linking API, and replaying stolen content — because none of those attacks touch the actual mechanism (an internal slot) the guard checks.
