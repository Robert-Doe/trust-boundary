Deep Dive · Trusted Types + PrototypesInternal Slots: A Pattern Bigger Than Trusted Types

Module 22 found that a Trusted-Types-guarded sink doesn't rely on instanceof. It turns out this isn't a one-off design choice invented for Trusted Types — it's the SAME pattern JavaScript's own built-in Map uses, and we can verify that directly, the same way this course verifies everything else.

The exact same forgery, against Map instead of TrustedHTML

node -e "..." → actual stdout
const fakeMap = Object.create(Map.prototype);
fakeMap instanceof Map;      // true  ← spoofed, exactly like Module 22's TrustedHTML forgery
fakeMap.get('x');            // THROWS:
// TypeError: Method Map.prototype.get called on incompatible receiver #<Map>

Same shape, same result: passes instanceof, still rejected by the real method — because Map.prototype.get, like a Trusted Types sink, doesn't trust the prototype chain. It checks for an internal slot (informally called [[MapData]] in the spec) that only a real new Map() construction ever sets.

The general pattern, and why it exists everywhere it does

ECMAScript defines internal slots as state that exists ON a spec-level object but is explicitly NOT exposed as an ordinary property — no key you can enumerate, no descriptor you can copy, nothing Object.create or Object.setPrototypeOf can ever set from outside the one algorithm authorized to. Built-ins that maintain some invariant they can't allow arbitrary code to fake almost always use this pattern:

Built-inWhat the internal slot protects
PromiseIts resolution state — so .then() can't be tricked into treating a plain object as an already-settled promise
Map / SetIts actual key/value storage — verified above
ArrayBuffer / typed arraysThe real underlying byte buffer — prevents a fake object from claiming to own memory it doesn't
DateIts internal numeric timestamp, independent of any property you could set on a fake date-like object
TrustedHTML / TrustedScript / TrustedScriptURLVerified in Module 22 — the wrapped, policy-approved content

Why this matters beyond trivia

Recognizing this pattern means you can predict, without testing every single built-in individually, which JS APIs are likely to resist prototype-based forgery (anything guarding a real invariant it can't let arbitrary code fake) versus which are just ordinary objects/classes you wrote yourself, where instanceof really is the whole check (and really is exactly as forgeable as the prerequisites page warned). Trusted Types isn't a special exception to how JavaScript works — it's an application of a well-established, decades-old platform pattern to a new problem.
