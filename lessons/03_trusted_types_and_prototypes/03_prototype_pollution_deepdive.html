Deep Dive · Trusted Types + PrototypesPrototype Pollution as a General JS Vulnerability Class

Don't over-generalize Module 23's finding Module 23 proved prototype pollution specifically CANNOT forge a Trusted Types value. That is a narrow, verified claim about ONE mechanism. This page is about the much broader, very real vulnerability class prototype pollution belongs to — where it absolutely CAN cause real damage, in code that isn't protected by an internal slot.

The general shape of the vulnerability

Prototype pollution vulnerabilities typically arise in utility functions that recursively merge or set properties on objects using attacker-controlled KEYS — a "deep merge," "extend," or "set nested property by path" function that doesn't guard against the key literally being the string "__proto__" (or "constructor" / "prototype", reaching the same place a different way). 

function unsafeMerge(target, source) {
  for (const key in source) {
    if (typeof source[key] === 'object') {
      target[key] = target[key] || {};
      unsafeMerge(target[key], source[key]); // recurses into target["__proto__"]!
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
unsafeMerge({}, JSON.parse('{"__proto__":{"polluted":"yes"}}'));
({}).polluted; // "yes" — EVERY object in the process now has this

This is the exact mechanic Module 23's Attack A used deliberately, on purpose, to test Trusted Types — but here it arrives by accident, through attacker-controlled JSON reaching an unguarded merge function.

Why this became a well-known, widely-patched vulnerability class

Several widely-used JavaScript utility libraries — most notably several versions of Lodash's deep-merge/defaults functions — had real, disclosed prototype pollution vulnerabilities patched over the years, because their recursive merge logic didn't special-case dangerous keys. Because these utilities sit underneath enormous numbers of applications, a pollution bug in one shared dependency could affect any application using it, without that application's own code containing any obviously "unsafe" pattern itself.

Where pollution actually causes damage — the code that trusts it

Pollution by itself is inert until something downstream TRUSTS the polluted state. Real damage patterns include:

  • Property-presence checks used as authorization: code like if (user.isAdmin) { ... } — pollution can inject isAdmin onto every object, including ones that never legitimately had it set.
  • Configuration objects with silently-inherited defaults: a library that reads options.someFlag without an Object.hasOwn check may read an attacker-injected value instead of its intended default.
  • Template engines and other code that eventually reaches a dangerous sink: some real disclosed exploit chains combined prototype pollution with a downstream template-rendering or `child_process` call that trusted a polluted configuration value, turning a "just" pollution bug into remote code execution.

Why "internal-slot-guarded" code (like Trusted Types) is immune, and ordinary code usually isn't

The reason Module 23's attack failed against Trusted Types is specific and narrow: the sink's real check never consults any property reachable through the prototype chain AT ALL, polluted or not. Ordinary application code, almost by definition, DOES read properties through the prototype chain constantly — that's what makes JavaScript's object model convenient day to day. The defense against prototype pollution for your OWN code isn't "hope it behaves like Trusted Types" — it's concrete, standard mitigations: use Object.create(null) for objects meant purely as key/value maps, use Map instead of plain objects for untrusted-keyed data, use Object.hasOwn(obj, key) rather than key in obj or truthy checks, and reject "__proto__"/"constructor"/"prototype" as keys explicitly in any merge/set-by-path utility that accepts external input.
