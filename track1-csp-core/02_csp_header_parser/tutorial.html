01 — The Big Analogy

A CSP header is a sentence written in a very small, very rigid language — closer to a customs declaration form than to prose. Customs doesn't try to understand your intent; it reads field by field, in a fixed order, and if a field is blank it just moves to the next one. It doesn't judge whether your declared items make sense together — that's a different official's job, later, at a different desk.

This module is that first customs officer. It reads the raw header string field by field (split on ;, then on whitespace) and produces a clean form (a JS object) — nothing more. Whether the declared values actually get allowed through is Module 3's job, at a different desk, with the browser standing behind it.

02 — What Happens, Step by Step

  1. parseCSP(headerValue) receives the raw header string, e.g. "default-src 'self'; script-src 'self' https://cdn.example.com".
  2. Split the whole string on ; → a list of raw directive chunks, some possibly empty (from ;; or a trailing ;).
  3. For each chunk: trim it; if empty, skip it entirely.
  4. Split the trimmed chunk on whitespace. Token 0 is the directive name; lowercase it. The rest of the tokens are source expressions, kept as-is.
  5. If this directive name was already seen earlier in the same policy, drop this occurrence — first one wins.
  6. Otherwise, store name → [sources] in the result object.
  7. Return the finished object once every chunk has been processed.

04 — The Code, Explained

The whole parser — src/csp-parser.js:

for (const raw of rawDirectives) {
  const trimmed = raw.trim();
  if (trimmed === '') continue; // rule 4

  const tokens = trimmed.split(/\s+/); // rule 2
  const name = tokens[0].toLowerCase(); // rule 3
  const sources = tokens.slice(1);

  if (Object.prototype.hasOwnProperty.call(policy, name)) continue; // rule 5

  policy[name] = sources;
}

Every numbered rule comment traces back to the CSP spec, not to our preference — see DECISIONS.md for the exact spec-vs-convention breakdown of every line.

07 — Brain Exercise

Think it through before revealing

Given parseCSP("script-src 'self'; script-src *"), our parser returns {"script-src": ["'self'"]} — the stricter first occurrence wins, the looser * is dropped. Now suppose an attacker who controls part of your response headers (say, through a header-injection bug elsewhere in your stack) could append ; script-src * to your existing policy. Could they use that to loosen your CSP?

Reveal the answer:

No — and this is exactly why "first occurrence wins" is the safer of the two possible spec choices. If it were "last occurrence wins" instead, appending a second script-src * to the end of a header would silently override your real policy with a wide-open one. Because the spec chose first-wins, an attacker who can only append to your header (not rewrite the whole thing) can only add directives that get ignored if you already declared them — they can't loosen anything you already restricted. They could still add a brand-new directive you never set at all, though, which is why this is a mitigation for one specific injection shape, not a substitute for stopping header injection in the first place.

08 — There Are No Dumb Questions

Q: Why not use a real parsing library or regex-only one-liner?

A one-liner regex could match the happy path, but "first duplicate directive wins" and "empty chunks are skipped" are stateful rules that need a loop with memory, not a single pattern match. Writing it by hand also means every rule has a comment pointing at *why* it exists — a borrowed library wouldn't teach you anything.

Q: Does this parser validate that `'self'` or `https://cdn.example.com` are well-formed source expressions?

No, deliberately. It stores whatever token appears after the directive name, even garbage like 'slef' (a typo). Validating *shape* is a different, optional concern this module doesn't need to solve — Module 3 only cares whether a given load matches a source expression, and a malformed one simply never matches anything, which is a safe failure mode.

Q: What happens with an empty string input, `parseCSP("")`?

Try tracing it through the code: "".split(';') is [""], the single chunk trims to "", which the empty check skips — so it returns {}. An empty policy object, not a crash. That matters because a server that accidentally sends an empty CSP header should be treated as "no directives declared," not blow up Module 3's code that consumes this output.

Q: Is "first occurrence wins" something we could double check for ourselves?

Yes — and we do, for real, in Module 3, by sending an actual header with a duplicated directive to a real browser and observing which one gets enforced, rather than trusting the spec text alone.

09 — What's Next

Module 3 takes this exact parser's output shape and does something Module 2 never touches: it sends real Content-Security-Policy headers from a real server and watches a real browser enforce them — blocking some of Module 1's four proofs while leaving others intact. That's where "parsed correctly" turns into "actually restricts something."
