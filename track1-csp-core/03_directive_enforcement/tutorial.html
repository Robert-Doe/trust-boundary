01 — The Big Analogy

Back to Module 1's apartment building. This module is the day the front desk finally opens. A sign goes up: "Only residents (badge = 'self') may enter units. No outside deliveries accepted at the door." The building's rooms, hallways, and furniture haven't changed at all — what changed is that now someone is checking badges before letting anyone through, and turning away everyone who doesn't have one.

Critically: the front desk doesn't know or care why a resident wants to enter their own unit — it only checks the badge. That's why Proof E (a same-origin script) sails through unchanged while Proofs A–D, all attempts to use unbadged or self-authored-on-the-spot entry, get turned away.

02 — What Happens, Step by Step

  1. Server sends Content-Security-Policy: default-src 'self'; script-src 'self' as a real response header alongside the HTML body.
  2. violation-listener.js loads first (before anything else) and starts buffering every securitypolicyviolation event.
  3. Browser parses the body. Inline <script> (Proof A): blocked before it runs — no 'unsafe-inline'.
  4. <script src="http://localhost:5400/attacker.js"> (Proof B): blocked before the fetch even completes — 5400 isn't 'self'.
  5. <img src="http://localhost:5400/pixel.png"> (Proof C): blocked under the img-src fallback from default-src.
  6. wiring.js (same-origin, allowed) loads and runs. It drains the buffered violations into the on-page log, then calls eval('1 + 1') automatically (Proof D): throws EvalError — no 'unsafe-eval'.
  7. same-origin-proof.js (Proof E) loads and runs normally — 'self' covers it.

04 — The Code, Explained

The header, sent for real — server.js:

const POLICY = "default-src 'self'; script-src 'self'";
// ...
const headers = { 'Content-Type': MIME[ext] || 'application/octet-stream' };
if (sendCSP) headers['Content-Security-Policy'] = POLICY;
res.writeHead(200, headers);

The listener that has to load first — public/violation-listener.js:

window.__cspViolations = [];
document.addEventListener('securitypolicyviolation', (e) => {
  window.__cspViolations.push({
    blockedURI: e.blockedURI,
    violatedDirective: e.violatedDirective,
    effectiveDirective: e.effectiveDirective,
  });
});

The eval probe that runs unconditionally, not just on click — public/wiring.js:

function runEvalProbe() {
  const el = document.getElementById('eval-proof');
  try {
    const result = eval('1 + 1');
    el.textContent = 'eval result: ' + result + ' (should NOT happen under this policy)';
  } catch (e) {
    el.textContent = 'BLOCKED: ' + e.name + ': ' + e.message;
  }
}
document.getElementById('eval-btn').addEventListener('click', runEvalProbe);
runEvalProbe(); // auto-run once on load — this is the run the tutorial documents

07 — Brain Exercise

Think it through before revealing

We built this module's Proof D to run automatically on page load instead of only from a button click. Why wasn't "just click the button and check the result" good enough — what specifically could go wrong with only testing it that way?

Reveal the answer:

We actually hit this for real: testing via this course's own browser automation, calling element.click() through Chrome DevTools Protocol's Runtime.evaluate, made eval('1 + 1') return 2 — CSP did not block it. That's because DevTools/CDP- injected script execution is treated by Chromium as trusted operator input, exempt from the page's own script-src restriction on eval, and that exemption applies to anything called synchronously from within that injected call, including our click handler. A human physically clicking the button in a real browser window would NOT get this exemption — only automation tooling built on the same protocol path does. Since we needed a result we could trust and reproduce consistently regardless of how the page is being driven, we made the probe run as part of the page's own normal load sequence — genuine page script, no external trigger, no exemption possible.

08 — There Are No Dumb Questions

Q: If `default-src 'self'` already covers `img-src` by fallback, why did we also write `script-src 'self'` explicitly, when it's the same value?

To exercise the override rule from the prerequisites page on purpose: an explicit script-src fully replaces the fallback for scripts specifically, even when it happens to say the same thing. Writing it out makes that override visible in the header text itself, instead of leaving a reader to wonder whether scripts are "really" governed by default-src or not.

Q: The image proof (C) never got wired up to show "FAILED to load" — is that a bug?

It's the same load/attach-order issue documented for the violation log: the image starts loading (and failing) before wiring.js's error handler ever attaches. We chose not to "fix" this one further, because the violation log entry (#1 blockedURI=http://localhost:5400/pixel.png) already proves the block — it's a good live example of exactly the ordering gotcha this module's DECISIONS.md discusses, left visible on purpose.

Q: Why does the violation event call the image block's directive `img-src` but the script blocks `script-src-elem`, not just `script-src`?

effectiveDirective reports the most specific directive the browser actually checked against — `script-src-elem` governs `<script>` elements specifically (there's a sibling `script-src-attr` for `on*=""` attributes), while our policy only declared the broader `script-src`, which both of those fall back to. `img-src` has no such sub-directives, so it's reported plainly.

Q: Could an attacker who controls the *content* of `attacker.js` do anything, given it never even loads?

No — that's the point being proven. The browser refuses the fetch/execute before a single byte of that file's content matters. Under this policy, what `attacker.js` contains is irrelevant; only Module 5+ start caring about content-based allowlisting (hashes).
