01 — The Big Analogy

Picture a fire-drill smoke detector installed a week before the real one: it still senses smoke, still sounds an alert to the building manager's office, still logs exactly which floor and which sensor tripped — but it doesn't trigger the sprinklers or lock the fire doors. You get to see, with real data from your actual building, what would have gone off and how often, before you ever risk soaking someone's desk over burnt toast.

That's Content-Security-Policy-Report-Only. Same detection logic as the enforcing header, same events, same log — just the "sprinklers" (the actual blocking) disconnected.

02 — What Happens, Step by Step

  1. Server sends the identical policy string as Module 3, but under the header name Content-Security-Policy-Report-Only instead of Content-Security-Policy.
  2. Browser parses the body. Every action that would have violated the enforcing policy (inline script, cross-origin script, cross-origin image, eval) is allowed to proceed normally.
  3. For each of those same actions, the browser also fires a securitypolicyviolation DOM event — same shape as Module 3's — but this time with event.disposition === "report" instead of "enforce".
  4. Our violation log renders all four events with their disposition field visible, so you can see the "would have been blocked, wasn't" signal directly.

04 — The Code, Explained

The one-line difference that drives everything else — server.js:

if (headerName) headers[headerName] = POLICY;
// Module 3 called this with headerName: 'Content-Security-Policy'
// Module 4 calls it with headerName: 'Content-Security-Policy-Report-Only'
// POLICY itself never changes.

The new field we capture to prove the mode, not just the outcome — public/violation-listener.js:

window.__cspViolations.push({
  blockedURI: e.blockedURI,
  violatedDirective: e.violatedDirective,
  effectiveDirective: e.effectiveDirective,
  disposition: e.disposition, // "enforce" or "report" — this module's key new field
});

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Actually protect anything — report-only, by definition, blocks nothing
  • Send these violation reports to a server automatically (Module 10's Reporting API)
  • Run enforce and report-only policies side by side to compare a policy CHANGE (that's a real deployment pattern, out of scope here)

✓ CAN DO

  • Test a new, stricter policy against real page behavior with zero risk of breaking anything
  • Distinguish "would this have been blocked" from "was this blocked" using one field, disposition
  • Reuse literally the same policy string between enforce and report-only modes to isolate the variable

Getting a blank or broken result? If every proof shows "ALLOWED" but the violation log stays empty, double check the header name in your network tab — a typo like Content-Security-Policy-ReportOnly (missing the second hyphen) is silently ignored by browsers as an unrecognized header, which looks identical to "no CSP at all" (Module 1) rather than report-only.

07 — Brain Exercise

Think it through before revealing

Could a real production team ship Content-Security-Policy-Report-Only by itself, forever, as their actual XSS defense, and skip the enforcing header entirely?

Reveal the answer:

No — and this module's own data shows why. Every single proof that Module 3 blocked, this module's identical policy allowed to run to completion. An attacker's injected script doesn't care that a report got logged somewhere; it already executed by the time the report fires. Report-Only is a measurement tool for finding out what a policy would break before you turn it on — it has zero protective effect on its own. The two headers are almost always meant to be a before/after pair in a rollout process, not alternatives.

08 — There Are No Dumb Questions

Q: Can I send both headers at once — enforce one policy and report-only-test another?

Yes, and it's a common real pattern: ship a strict policy as Content-Security-Policy for real protection, while simultaneously sending an even-stricter candidate policy as Content-Security-Policy-Report-Only to see what breaks before promoting it. The two headers are independent; violations get evaluated and reported against each one separately.

Q: Does the browser send these reports anywhere by default, or do I need to configure something?

Nothing is sent anywhere by default — the DOM event we captured here is purely client-side and only visible to script running on the page. To get reports delivered to a server (which is the more common real use of report-only mode, checking logs rather than watching a live page), you add a report-to directive naming an endpoint — that's Module 10.

Q: Why did we bother re-verifying that Proof E produces no violation, when Module 3 already showed 'self' scripts are allowed?

Module 3 proved 'self' scripts are allowed under enforcement. This module needed to independently confirm they're not incorrectly flagged under report-only either — a report-only implementation that over-reported (flagged things that were never actually going to violate the policy) would be a real, plausible bug, and the only way to rule it out is to check, not assume symmetry.
