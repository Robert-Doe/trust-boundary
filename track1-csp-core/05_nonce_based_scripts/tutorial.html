01 — The Big Analogy

Think of a single-use event wristband, printed fresh at the door for tonight only, with tonight's stamp pattern that changes every single night. It doesn't matter that someone photographed last week's wristband — tonight's door staff only accepts tonight's exact pattern, generated moments before you walked in. A guest who shows up with an old wristband, a homemade one, or no wristband at all gets turned away identically.

That's a nonce. 'unsafe-inline' is "anyone in a wristband of any kind gets in" — it stopped meaning anything the moment it became guessable/universal. A nonce keyed to one specific response, generated by the server at the last possible moment, is what makes "allow *this one* inline script" different from "allow inline scripts."

02 — What Happens, Step by Step

  1. A request arrives. The server generates 16 random bytes via crypto.randomBytes and base64-encodes them into a nonce value, fresh for this response only.
  2. The server injects that exact nonce into the HTML template at every place a legitimate inline script needs it, AND into the CSP header as 'nonce-<value>'.
  3. Browser receives the response and starts parsing. It hits the first inline <script nonce="...> — the attribute matches the header's nonce exactly, so it runs.
  4. It hits a second inline <script> with no nonce attribute at all — no match possible, blocked.
  5. It hits a third inline <script nonce="wrong-nonce-value...">> — has an attribute, but the value doesn't match this response's nonce, blocked identically to the missing case.
  6. A same-origin external file loads separately, governed by 'self', no nonce involved at all.
  7. That file fires two more fetch('/') requests to the same URL, extracts the nonce each fresh response carries, and confirms they differ from each other and from the page's own.

04 — The Code, Explained

Fresh nonce per request — server.js:

const nonce = crypto.randomBytes(16).toString('base64');
const html = template.replaceAll('{{NONCE}}', nonce);
const policy = `script-src 'self' 'nonce-${nonce}'`;

Proving uniqueness by actually re-fetching, not by inspecting server code — public/wiring.js:

const [r1, r2] = await Promise.all([fetch('/'), fetch('/')]);
const n1 = extractNonce(r1.headers.get('content-security-policy'));
const n2 = extractNonce(r2.headers.get('content-security-policy'));
// n1 !== n2, verified — see DECISIONS.md for the real captured values

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Allowlist an inline script by its exact byte content instead of a per-response secret (Module 6: hashes)
  • Let a nonce-trusted script dynamically load further scripts without re-nonceing each one (Module 7: strict-dynamic)
  • Use nonces at all in a <meta>-tag CSP the same way — Module 9 covers the differences

✓ CAN DO

  • Allow exactly one inline script per response while blocking every other inline script, including copy-pasted attacker attempts
  • Prove, not assume, that the nonce actually changes every request
  • Distinguish "missing nonce" from "wrong nonce" as two independently-blocked cases

07 — Brain Exercise

Think it through before revealing

Suppose an attacker finds a reflected-XSS injection point on this exact page — somewhere your server echoes back a URL parameter unescaped into the HTML. Can they defeat this nonce-based policy by injecting <script nonce="S8dfa9RZScpyRn9UmeaeLA==">evil()</script> using today's real nonce value, which they just read out of this very page's HTML?

Reveal the answer:

Yes — and this is the sharp edge of nonce-based CSP that's easy to miss. If an attacker can read the current response's own HTML (which reflected XSS, by definition, requires them to inject INTO), they can also read the nonce value sitting right there in that same response's <script> tags, and stamp their injected script with it. The nonce defends against generic inline-script injection into a DIFFERENT unrelated response, and against attackers who can't see the current page's markup at all — it does not, by itself, stop an attacker who can inject directly into the very response carrying the valid nonce. This is exactly why Module 11 builds a real reflected-XSS scenario and is explicit about which layer of defense is actually doing the blocking there.

08 — There Are No Dumb Questions

Q: Why base64 instead of, say, a hex string?

No functional difference for CSP's matching (it's an exact string comparison either way) — base64 just packs more entropy per character, so a 16-byte random value renders as a shorter attribute string than the hex equivalent would. Purely a size/readability convention, not a security requirement.
