01 — The Big Analogy

A nonce (Module 5) was a wristband printed fresh at the door tonight. A hash is a completely different kind of proof: it's like a wax seal pressed directly into a letter's own content — melt the wax onto the exact words written, and anyone can verify later that the letter wasn't altered by re-melting a copy and comparing seals. Change even one word, and the new seal looks nothing like the old one. Nobody had to hand out the seal in advance, and nobody needs to remember it expired — the letter's own content IS the credential.

02 — What Happens, Step by Step

  1. Server defines ALLOWED_SCRIPT, one fixed JS string, and computes its SHA-256 hash once (deterministic — the same string always produces the same hash).
  2. That hash goes into the CSP header as 'sha256-<value>', and the identical string is injected verbatim into the one <script> tag it belongs in.
  3. Browser parses the body, reaches that script tag, hashes its actual content itself, and compares the result to the policy's allowlisted hash — match, so it runs.
  4. Browser reaches a second inline script whose content looks almost identical but has one extra trailing space. Its hash comes out completely different (SHA-256 has no "close enough") — no match, blocked.
  5. A same-origin external script re-fetches the page twice and compares the hash each response's header carries — confirms it's identical both times, unlike Module 5's nonce.

04 — The Code, Explained

One string, hashed once, injected verbatim — server.js:

const ALLOWED_SCRIPT =
  "document.getElementById('correct-hash-proof').textContent = '...'; ...";
const hash = crypto.createHash('sha256').update(ALLOWED_SCRIPT, 'utf8').digest('base64');
// ...
const html = template.replaceAll('{{ALLOWED_SCRIPT}}', ALLOWED_SCRIPT);
const policy = `script-src 'self' 'sha256-${hash}'`;

The bug we caught before ever running this module — public/index.html, the fixed version:

<!-- Proof A: this <script> tag's ENTIRE text content must be byte-for-byte
     identical to the ALLOWED_SCRIPT string server.js hashed — nothing
     added, nothing removed, not even a listener setup line. -->
<script>{{ALLOWED_SCRIPT}}</script>

Full story of that near-miss in DECISIONS.md — it's a real mistake this course made and fixed, not a hypothetical.

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Allowlist a whole family of dynamically-inserted scripts from one trusted root (Module 7)
  • Hash-allowlist something that changes per response — that's what nonces are for
  • Tolerate even whitespace-only edits without regenerating the hash

✓ CAN DO

  • Allowlist a fixed inline script with zero server-side randomness or state
  • Guarantee the same content always produces the same allowlist entry, verified across requests
  • Catch a content/hash mismatch as a hard block instead of a silent security hole

07 — Brain Exercise

Think it through before revealing

A teammate suggests: "Hashes seem strictly better than nonces — no server-side randomness needed, no per-request state to manage. Let's just hash-allowlist everything and drop nonces entirely." What inline-script use case would break under that plan?

Reveal the answer:

Any inline script whose content legitimately changes per response — for example, one that embeds a CSRF token, a per-user greeting, or any server-rendered dynamic value directly in its source. A hash is tied to exact bytes; if the content is different every time by design, you'd need a different hash every time too, which means recomputing and re-sending a changing CSP header per response anyway — at which point you've reinvented a nonce, just clumsily, with extra hashing overhead and no actual benefit. Hashes suit content that's fixed at deploy time; nonces suit content that's generated at request time. Neither replaces the other.
