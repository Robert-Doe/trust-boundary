01 — The Big Analogy

An HTTP header is a security briefing handed to the building's staff before the doors open — everyone inside knows the rules from minute zero. A <meta> CSP is more like a policy notice posted on a bulletin board partway down a hallway — anyone who already walked past that point before it went up never saw it, and some rules (like "no photographing the building from outside," analogous to frame-ancestors) can't be enforced by a bulletin board no matter how clearly it's worded — that's a perimeter-security decision, not something a sign inside the building can control.

02 — What Happens, Step by Step

  1. Browser starts parsing HTML. An inline script before any <meta> CSP tag runs — nothing has restricted it yet.
  2. Parser reaches <meta http-equiv="Content-Security-Policy" content="script-src 'self'; frame-ancestors 'none'"> and activates that policy from this point forward.
  3. Browser also immediately determines it cannot enforce frame-ancestors via <meta> at all, and logs a warning saying so — the directive is silently dropped, not silently "best-effort applied."
  4. An inline script written after the <meta> tag is now blocked by the active script-src 'self'.
  5. On a separate page, a <meta http-equiv="Content-Security-Policy-Report-Only"> tag is parsed — and produces neither a blocked action NOR a violation event. The browser logs that it disallowed and ignored the entire policy.

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Protect content that appears before the `<meta>` tag in the document
  • Enforce `frame-ancestors`, `report-to`/`report-uri`, or `sandbox` via `<meta>` at all
  • Use Report-Only mode via `<meta>` — it's flatly disallowed, not just weaker

✓ CAN DO

  • Ship a real, enforcing CSP from environments where you can't control HTTP response headers
  • Correctly predict which of the three directive families silently won't work there
  • Recognize the specific "policy notice, not perimeter security" shape of what `<meta>` can and can't do

07 — Brain Exercise

Think it through before revealing

A team ships a strict CSP via <meta> because their static host doesn't let them set custom HTTP headers. Their policy includes frame-ancestors 'none', and they believe this protects them from clickjacking. Are they actually protected?

Reveal the answer:

No — and this is a real, dangerous gap this module's Proof C exists to surface. `frame-ancestors` is silently ignored when delivered via `<meta>`; the browser logs a console warning, but nothing in the page's actual behavior changes, and most teams never open DevTools on a production page to notice a console warning that isn't an error. The team in this scenario has zero clickjacking protection despite their policy explicitly declaring `frame-ancestors 'none'` — the directive is present in their source code and completely inert at runtime. This is exactly why Module 12, which covers `frame-ancestors` in depth, matters even to teams already using `<meta>` CSP: they need a different delivery mechanism for that one directive specifically, or an `X-Frame-Options` header as a fallback (a separate, older, header-only mechanism).

08 — There Are No Dumb Questions

Q: Can I put the `<meta>` CSP tag as the very first thing in `<head>` to avoid the "before/after" gap entirely?

Yes — and that's the practical mitigation for Proof A/B's gap: place the `<meta>` tag as early as structurally possible (ideally right after `<meta charset>`) so as little content as possible parses before it activates. It doesn't eliminate the category of gap, but it minimizes its window.

Q: Do multiple `<meta>` CSP tags on one page combine the same way Module 8's two headers did?

Yes — the same intersection rule applies. Each `<meta>` CSP tag the parser encounters becomes another independently-enforced active policy, exactly like a second header line, combining by AND with everything already active (including any header-delivered policy on the same page).

Q: Why does the browser bother logging a console warning for something it's just going to ignore anyway?

It's a real, if imperfect, mitigation for exactly the Brain Exercise scenario above — a developer who does check their console during development has a chance to notice the directive is dead. It doesn't help in production, where almost nobody has DevTools open, which is precisely why relying on the warning instead of avoiding the gap in the first place is not a real fix.
