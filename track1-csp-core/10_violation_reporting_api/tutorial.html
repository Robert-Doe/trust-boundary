01 — The Big Analogy

A ship's black-box flight/voyage recorder captures a detailed, accurate log of every incident the instant it happens — that part is immediate and reliable, by design. Whether that recorder's data ever reaches an investigator, though, depends on a completely separate process: someone has to physically recover the box, or it has to successfully transmit over a connection that might not even be available yet. This module is about discovering, directly, which of those two very different guarantees CSP's reporting actually gives you — and it turned out to matter enormously which one we were checking.

02 — What Happens, Step by Step

  1. Server sends a policy with both a legacy report-uri /csp-report directive and a modern report-to csp-endpoint directive, plus a Reporting-Endpoints header naming that group's real URL.
  2. Two deliberate violations occur (inline script, eval).
  3. A page-level ReportingObserver immediately captures full, detailed report objects for both violations — this happens synchronously, reliably, with zero network involvement.
  4. We poll our own collector server's /debug/reports endpoint for several seconds. Nothing arrives.
  5. We wait longer, then force a navigation away (in case delivery happens on unload), then check the collector server's raw log directly. Still nothing arrived, by either mechanism.

04 — The Code, Explained

Testing both mechanisms without assuming either works — server.js:

const POLICY = "default-src 'self'; script-src 'self'; report-uri /csp-report; report-to csp-endpoint";
const REPORTING_ENDPOINTS = 'csp-endpoint="http://localhost:6500/csp-report"';

The tool that isolated generation from delivery — public/wiring.js:

const observer = new ReportingObserver((reports) => {
  reports.forEach((r) => observed.push({ type: r.type, url: r.url, body: r.body }));
}, { buffered: true });
observer.observe();

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Assume a collector endpoint receiving nothing means no violations occurred
  • Use a live collector as a real-time development debugging tool
  • Rely on any specific delivery timing — the spec explicitly doesn't guarantee one

✓ CAN DO

  • Get an immediate, complete, reliable local signal via `ReportingObserver` — no network or server required at all
  • Build a real server-side collector endpoint that will log whatever DOES eventually arrive, in production, at scale, over time
  • Correctly distinguish "the browser detected this violation" from "a server received a report about it" as two different claims

Getting a different result on your machine? If your collector DOES receive reports where ours didn't, that's genuinely interesting, not a sign something's broken — it would mean your browser's network-reporting behavior differs from the environment this course verified in (real Chrome, outside an automated test harness, seems the most likely candidate to behave differently). Either outcome is consistent with the spec, which is precisely this module's point: don't build anything that assumes a specific delivery timing.

07 — Brain Exercise

Think it through before revealing

A teammate says: "I added report-to to our CSP header last week and our collector dashboard still shows zero events — the feature must be broken." Given everything this module verified, what's a more likely explanation, and how would you actually check?

Reveal the answer:

The feature working and reports being delivered promptly are two different claims, and this module showed real reports get generated and can go completely undelivered, at least for a while, with no error surfaced anywhere. Before concluding "broken," check the two halves separately: (1) does `new ReportingObserver(cb, {buffered:true}).observe()` on the live page show real report objects when you trigger a known violation? If yes, generation works fine, and the question becomes purely about the network path — a firewall, an ad-blocker (browsers' own "Failed to load resource" noise in this module's own console log — from an ad-blocker-style extension — is a hint this can be blocked client-side too), a misconfigured endpoint URL, or simply the browser's own upload timer not having fired yet. Checking "does my collector have anything" alone can't distinguish "broken" from "not delivered yet" from "actively blocked" — you need the generation-side signal too.

08 — There Are No Dumb Questions

Q: Why keep BOTH `report-uri` and `report-to` in a real production policy, if `report-uri` is legacy?

Browser support gap coverage: older browsers only understand `report-uri`; newer ones prefer `report-to`/`Reporting-Endpoints`. Declaring both costs nothing (unrecognized directives are just ignored) and maximizes the chance SOME mechanism delivers on SOME visitor's browser.

Q: Is it suspicious that we saw `net::ERR_BLOCKED_BY_CLIENT` messages in the console during this module?

Those appeared in every module in this course from the very first one — they're this specific browser environment's own extension-level noise (consistent with an ad-blocker-style filter), unrelated to CSP. We call this out explicitly here because "reports aren't arriving" plus "BLOCKED_BY_CLIENT in the console" is exactly the pattern that would mislead someone into blaming an ad-blocker for this module's real, independently-confirmed finding (zero delivery even after ruling out timing).

Q: Does `disposition: "enforce"` in the ReportingObserver output mean the same thing as Module 4's `event.disposition`?

Yes — same concept, same two possible values (`"enforce"`/`"report"`), just visible through a different API. `ReportingObserver` and the DOM `securitypolicyviolation` event are two independent ways of observing the same underlying violation; nothing about report generation is exclusive to one or the other.
