01 — The Big Analogy

This module is the full-scale fire drill after nine modules of testing individual smoke detectors. Same building (the identical broken code, both times), same fire (the identical malicious link), one crucial difference: whether the suppression system (CSP) is armed. This is the module where you stop trusting that the individual pieces work and watch the whole chain — crafted link, unescaped server code, browser parser, CSP enforcement — play out for real, twice, side by side.

02 — What Happens, Step by Step

  1. A malicious link is crafted in advance: /vulnerable?q=<script>document.title='XSS-EXECUTED';</script>.
  2. The server reflects the q parameter directly into the HTML response, completely unescaped — a real, textbook reflected-XSS bug.
  3. Against /vulnerable (no CSP), the browser parses the injected <script> tag as a real element and executes it — the tab title changes to "XSS-EXECUTED".
  4. The exact same link, with only the path changed to /protected, hits a route serving the identical unescaped reflection — but now with script-src 'self' 'nonce-<fresh>' attached.
  5. The injected script has no nonce attribute (the attacker crafted this link before that response's nonce even existed) — blocked. Tab title stays "Search Results".

04 — The Code, Explained

The bug, present identically on both routes — server.js:

<p>You searched for: ${q}</p>
<!-- q is inserted RAW. No escaping. On EITHER route. -->

The only actual difference between the two routes:

const policy = csp ? \`script-src 'self' 'nonce-${'${nonce}'}'\` : null;
// ...
if (route.policy) headers['Content-Security-Policy'] = route.policy;

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Call this "fixed" — the injection bug is still live on both routes; only the browser-side consequence changed
  • Defend against an attacker who can read a specific response's nonce before crafting their payload against that SAME response (a narrower, different scenario)
  • Protect a sink like `innerHTML` from a DIFFERENT kind of injection that never goes through `<script>` parsing at all — that's Track 2's job

✓ CAN DO

  • Watch a real, working exploit succeed and fail against byte-identical vulnerable code
  • Point at exactly one header as the entire difference between "compromised" and "safe" for this attack shape
  • Explain precisely why a pre-crafted attack link can't include a not-yet-generated nonce

07 — Brain Exercise

Think it through before revealing

Given that this module proves CSP genuinely stops the exploit, why does DECISIONS.md insist the underlying bug should still be treated as a real, urgent problem to fix — rather than "handled" now that CSP is in place?

Reveal the answer:

Because CSP's protection here is scoped to exactly one attack shape: getting the browser to execute injected script. The unescaped reflection bug is a general HTML-injection vulnerability, and HTML injection has consequences CSP doesn't touch at all — an attacker could still inject `<style>` to visually deface the page (subject to `style-src`, separately), inject a convincing fake login form (no code execution needed to phish, just misleading real HTML), or, if some other page ever combines this same endpoint with a looser policy or none at all, the ORIGINAL vulnerability is sitting there ready to be fully exploited again the moment the CSP is misconfigured, removed, or bypassed by a mechanism this course hasn't covered yet. CSP is real, valuable defense in depth — the "in depth" part means it's a second layer, not a replacement for fixing the first one.

08 — There Are No Dumb Questions

Q: Could `/protected`'s CSP have used a hash instead of a nonce here?

No — and this is a real, structural reason, not just a style preference. A hash allowlists one exact, known-in-advance script content string. The attacker's payload is arbitrary and unknown to the server ahead of time (it comes from user input), so there's no fixed content to hash in advance. Nonces work here specifically because they don't need to know the payload — they just require a secret the attacker can't predict.

Q: What if the attacker's payload didn't use a `<script>` tag at all — say, an `<img src=x onerror="...">`?

Still blocked, by the same `script-src` directive — inline event-handler attributes like `onerror="..."` are governed by `script-src` too (specifically, in stricter configurations, a `script-src-attr` sub-directive), and neither a nonce nor `'unsafe-inline'` is present to permit it. We used a plain `<script>` tag because it's the clearest textbook example, not because it's the only payload shape CSP happens to catch.

Q: Is `document.title` a realistic thing a real attacker would target?

No — it's a harmless, easily-observed stand-in for "attacker-controlled JavaScript executed in the victim's browser, in the victim's session, with the victim's cookies and DOM access." A real payload would more likely exfiltrate `document.cookie`, submit forms on the victim's behalf, or redirect the page — the tab title just makes success/failure trivially verifiable from outside the page for this course's purposes.
