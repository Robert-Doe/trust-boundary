01 — The Big Analogy

Clickjacking is the digital version of a fake "sign here for the free sample" clipboard that's secretly stacked on top of a real loan agreement, with a tiny hole cut exactly where your signature needs to land. You think you're signing for a sample; you're actually signing the real document underneath, which was rendered completely normally — nothing about the document itself was tampered with, it was just invisibly stacked under something else. frame-ancestors is the real document simply refusing to be placed under anything else at all: no stacking, no hole, no attack surface.

02 — What Happens, Step by Step

  1. An attacker page on a different origin embeds two iframes, each pointing at a different route on the victim's origin.
  2. For /open (no CSP), the victim server sends its response; the browser has no reason to refuse rendering it inside the frame, so it renders normally.
  3. For /protected, the victim server sends the SAME response shape, plus Content-Security-Policy: frame-ancestors 'none'.
  4. The browser receives that response (a real, successful 200) and then checks: is the current embedding context allowed by this response's own frame-ancestors value? 'none' means no context at all is allowed.
  5. The browser refuses to render the frame's content, logs a violation, and the network log shows the request failing AFTER a successful response — net::ERR_BLOCKED_BY_RESPONSE.

04 — The Code, Explained

The one header that changes everything — server.js:

if (req.url === '/protected') {
  res.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8',
    'Content-Security-Policy': "frame-ancestors 'none'",
  });
  return res.end(victimPage('/protected (frame-ancestors: none)'));
}

Why we didn't try to prove this via reading the iframe's DOM — see DECISIONS.md; the real proof came from the network log and console instead:

GET http://localhost:6700/open      → 200 OK
GET http://localhost:6700/protected → 200 OK [FAILED: net::ERR_BLOCKED_BY_RESPONSE]

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Deliver this same protection via `<meta>` — Module 9 already proved `frame-ancestors` is silently ignored there
  • Allow SPECIFIC trusted origins to frame the page while blocking everyone else — that needs `frame-ancestors https://trusted.example` instead of `'none'`, untested in this module
  • Stop an attacker from linking directly to your page (frame-ancestors only governs EMBEDDING, not navigation)

✓ CAN DO

  • Completely prevent a page from being framed by any origin, closing the entire clickjacking attack surface for that page
  • Verify the block via real network status, not just trust the console message alone
  • Correctly explain WHY this defense has nothing to do with script-src/style-src at all

07 — Brain Exercise

Think it through before revealing

This module's older, simpler cousin is the X-Frame-Options header (values like DENY or SAMEORIGIN), which does roughly the same job and predates CSP. Given that frame-ancestors exists and does more (it can allowlist specific origins, not just same-origin-or-nobody), should a real site drop X-Frame-Options entirely once it adds frame-ancestors?

Reveal the answer:

Not immediately, and the reasoning is pure defense-in-depth: browsers that don't understand `frame-ancestors` at all (very old, but some still exist in the wild depending on your users) will simply ignore that unrecognized directive and offer NO clickjacking protection at all if it's the only mechanism present. `X-Frame-Options` has near-universal support, even in browsers old enough to predate CSP entirely. Real-world guidance is typically to send both — `frame-ancestors` for browsers that understand it (more expressive, the modern standard), `X-Frame-Options` as a safety net for the ones that don't. This is a genuinely different kind of "send two things" than Module 8's policy intersection — these are two entirely separate HTTP headers using two entirely separate mechanisms, aimed at the same goal.

08 — There Are No Dumb Questions

Q: Does `frame-ancestors 'none'` also stop the page from opening in a regular new tab, or being linked to directly?

No — `frame-ancestors` only governs being embedded as a frame/iframe/object inside another document. Navigating directly to the URL, clicking a normal link, or opening it in a new tab are unaffected; those aren't "framing" in the sense this directive checks.

Q: Why did the network log show `200 OK` and THEN a failure, instead of the browser refusing to even connect?

Because `frame-ancestors` is a property of the response the browser has to actually receive before it can check — the victim server doesn't know or care who's trying to frame it; it just serves its normal response with the policy attached, every time. The embedding browser is the one enforcing the rule, after the fact, based on the header it just received. That's a fundamentally different enforcement point than, say, a server that checked the `Referer` header and refused to respond at all — a real, older, much weaker anti-framing technique.

Q: Could the victim server have used `frame-ancestors 'self'` instead of `'none'` to allow framing itself?

Yes — `'self'` is a completely valid and common choice, useful for sites that legitimately embed their own pages in their own iframes (a preview pane, a multi-panel dashboard) but still want to block every OTHER origin. We used `'none'` here because this module's victim has no legitimate reason to ever be framed at all, making the strictest option the clearest demonstration.
