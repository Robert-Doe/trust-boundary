01 — The Big Analogy

Track 1's checkpoints (Module 3 onward) all check ID at the door: is this specific PERSON (this script, this frame, this form target) on the allowlist? A metal detector is a different kind of checkpoint entirely — it doesn't check who you are at all, it checks what category of OBJECT you're carrying, regardless of your identity. innerHTML is a door with no checkpoint of either kind: it lets absolutely anything through, and only certain things that get through later — specifically, things that try to actively DO something — run into Track 1's script-src checkpoint further inside the building. Something that just quietly changes the building's own signage never encounters a checkpoint at all.

02 — What Happens, Step by Step

  1. Server sends the strictest reasonable CSP from Track 1: script-src 'self' 'nonce-<fresh>', no exceptions.
  2. Page script assigns a string containing an <img onerror="..."> handler to innerHTML.
  3. The assignment itself succeeds instantly — innerHTML never inspects, validates, or refuses the string.
  4. When the browser later tries to actually FIRE that handler, THAT's the moment CSP's script-src-attr check runs — and blocks it.
  5. A second string, containing zero executable content (just a fake alert banner with a real link), is assigned to a different element's innerHTML.
  6. It renders completely, instantly, with no CSP check ever triggered — there was nothing in it for script-src to have jurisdiction over.

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Make `innerHTML` refuse a raw string at all, for any reason — nothing built so far can do that
  • Distinguish "safe HTML a developer trusts" from "unsafe HTML from user input" at the point of assignment
  • Get any signal (violation, error, warning) when non-executing HTML injection happens — it's completely invisible to every tool built in this course so far

✓ CAN DO

  • Correctly state exactly what CSP's script-src does and doesn't cover, based on direct verification rather than assumption
  • Recognize `innerHTML` (and its sink relatives) as accepting any string unconditionally, with zero built-in judgment
  • Identify the precise, narrow, real gap that motivates Trusted Types — not an exaggerated one

Getting a blank or broken result? If Proof B's banner doesn't render at all, check that you haven't accidentally set a `style-src` anywhere — this module's policy is script-src ONLY, and Proof B's markup uses a CSS class (not an inline style attribute) specifically so it isn't affected by that directive either way. If Proof A's handler DOES run, your browser or CSP implementation may not enforce `script-src-attr` the way this module's environment did — worth investigating further, not just dismissing.

07 — Brain Exercise

Think it through before revealing

Before writing this module, our working assumption was that CSP script-src leaves `innerHTML`-injected event handlers completely unblocked. Direct testing proved that assumption wrong. Why does this course choose to show you that wrong assumption and the correction, instead of just quietly writing the module around the correct answer from the start?

Reveal the answer:

Because the corrected finding is MORE useful precisely because it's narrower and more surprising than the naive version. "CSP doesn't stop DOM-XSS at all" is a common but imprecise claim that leads people to either distrust CSP more than they should, or to reach for Trusted Types for the wrong reason (to block script execution CSP was already blocking). The real, verified reason to want Trusted Types — that it governs ALL HTML structure reaching a sink, not just the executable parts — is a sharper, more defensible argument, and you only get to that sharper argument by actually testing the naive assumption and watching it fail. This is the same verification discipline the whole course runs on, applied to the course's OWN working assumptions, not just to claims about the browser.

08 — There Are No Dumb Questions

Q: Is a fake "Account Suspended" banner really a serious security issue, compared to actual code execution?

Yes, and arguably it's the harder one to defend against with traditional tools, precisely because it doesn't execute anything. Phishing via injected HTML doesn't need to steal a session token directly — it just needs to convince a user to hand over credentials on what looks like a legitimate page. No CSP directive is designed to judge whether rendered content is deceptive; that's a content/trust problem, not an execution problem.

Q: Does `document.write()` behave the same way as `innerHTML` for this module's purposes?

Yes, for the same underlying reason: both parse a string into real DOM/markup, and CSP's script-src still only governs what happens when something in that markup TRIES to execute — not whether the parse/insertion itself is allowed to happen. The prerequisites page on DOM sinks groups them together for exactly this reason.

Q: If script-src-attr already blocks the DANGEROUS parts, why do we need Trusted Types at all — isn't Proof B just "content," not really an attack?

Real attacks often combine both: HTML structure that LOOKS legitimate (Proof B's category) that ALSO happens to include something executable somewhere CSP might not perfectly cover, or that redirects to a page that then does more damage in a second step. Trusted Types' value isn't "catches the one thing CSP misses" — it's "makes the entire class of unreviewed-string-reaches-a-sink bugs impossible by construction," which is a stronger, earlier guarantee than reactively blocking specific dangerous behaviors after the string is already in the DOM.

09 — What's Next

Module 15 adds exactly one new CSP directive — require-trusted-types-for 'script' — and shows, for real, the browser refusing Proof B's exact same non-executing payload at the moment of assignment, before it ever becomes DOM. That's the mechanism this whole module has been building toward.
