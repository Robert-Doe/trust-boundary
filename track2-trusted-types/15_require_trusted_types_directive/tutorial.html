01 — The Big Analogy

Module 14's door had no checkpoint at all — anything walked through, unexamined. This module installs a checkpoint, but with an empty allowlist and no guard on duty to make exceptions: everyone gets turned away, the harmless delivery driver exactly as thoroughly as the person carrying something dangerous. That's not a useful final state — but it's the necessary first step, and it's the moment you can finally SEE the checkpoint exists at all, because now even completely innocent traffic bounces off it.

02 — What Happens, Step by Step

  1. Server adds exactly one new thing to the policy: require-trusted-types-for 'script'. No policy is created anywhere with trustedTypes.createPolicy().
  2. Page script attempts target_a.innerHTML = '<img onerror=...>' — same dangerous payload as Module 14's Proof A.
  3. The assignment throws immediately: TypeError: ... This document requires 'TrustedHTML' assignment. The string is a plain JS string, not a TrustedHTML object — the browser refuses it before even looking at what's inside.
  4. Page script attempts the exact same assignment with Module 14's Proof B — the completely harmless banner.
  5. Identical error, identical message. The browser can't tell them apart, because it never got far enough to try.
  6. eval('1+1') is attempted, with 'unsafe-eval' present in script-src (ruling out Track 1's separate mechanism) — throws a distinctly different Trusted-Types-specific error.

04 — The Code, Explained

The one directive that changes everything — server.js:

const policy = \`script-src 'self' 'nonce-${'${nonce}'}' 'unsafe-eval'; require-trusted-types-for 'script'\`;

Both proofs, same call shape as Module 14, now both throwing — server.js:

} catch (e) {

}

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Use `innerHTML` (or `eval`, or `script.src`) for ANYTHING — every guarded sink is now unconditionally broken
  • Distinguish safe from unsafe content — nothing is allowed through at all yet
  • Ship this to production as-is — a real app would break entirely

✓ CAN DO

  • Observe, with real error text, that Trusted Types enforcement is a real, active, categorical block — not a no-op
  • Confirm one CSP keyword governs BOTH HTML-type and Script-type sinks at once
  • Correctly predict Module 16's next necessary step: SOMETHING has to authorize sink assignments, or nothing on the page can use them

07 — Brain Exercise

Think it through before revealing

Proof A and Proof B produced byte-for-byte identical error messages. What does that identical wording tell you about WHEN, in the assignment process, the browser decided to block each one?

Reveal the answer:

It tells you the block happens before the browser has formed any opinion about the string's content at all — if it had inspected either string even briefly (looking for `<script>` tags, or handlers, or anything "suspicious"), you'd expect at least a chance of different error details between a payload containing a handler and one that doesn't. Identical errors mean the check that failed is purely about the VALUE'S TYPE — "is this a `TrustedHTML` object?" — answered the same way, immediately, for any plain JS string, dangerous-looking or not. This is the mechanistic core of Trusted Types: it's a type check at the API boundary, not a content scanner.

08 — There Are No Dumb Questions

Q: Why is the directive's value just `'script'` — not `'html'` or `'script-url'` for the different sink categories?

Because the spec defines exactly one value for this directive, and it turns on enforcement for every Trusted-Types-guarded sink category at once — HTML sinks (`innerHTML` etc.), Script sinks (`eval`, `Function`, inline event handler strings set via `.setAttribute`), and ScriptURL sinks (`script.src`) all become guarded together. There's no way to enable it for only one category.

Q: Is `TypeError` the right error class here, or should it be something CSP-specific like the `EvalError` we saw in Track 1?

Both appear, depending on the sink: HTML-type sinks throw a plain `TypeError` (a type-mismatch is exactly what happened — the sink demanded a `TrustedHTML` and got a string). `eval` throws `EvalError` specifically because that's the error class JS itself defines for problems with `eval`. Different sinks, different native error types, same underlying cause.

Q: Could a real site ship with `require-trusted-types-for 'script'` and no policies, on purpose?

Only as an intentional, extreme lockdown of a page/feature that should never use these sinks at all — any attempt (legitimate or malicious) simply fails. That's a real, valid use case for something like a purely static content page, but it's not the general-purpose story; Module 16 is what makes the mechanism usable for a normal application.
