01 — The Big Analogy

Module 15 built a checkpoint with an empty allowlist and no notary in the building at all. This module hires exactly one notary, gives them a named stamp, and defines precisely what they're allowed to certify. Anyone can still hand the notary a raw, unverified document — the notary's whole job is to look at it, apply their specific rule (maybe reformat it, maybe reject it, maybe pass it through), and hand back a stamped version. The checkpoint doesn't trust raw documents; it trusts the stamp, and the stamp only exists because the notary's rule function actually ran.

02 — What Happens, Step by Step

  1. trustedTypes.createPolicy('module16-demo', { createHTML: rule }) is called, where rule is a plain JS function that uppercases its input.
  2. It returns a TrustedTypePolicy object — an object, not a string, not a function itself.
  3. That object exposes createHTML, createScript, AND createScriptURL as callable methods — all three, even though only one rule was actually provided.
  4. Calling policy.createHTML('hello world') invokes our rule function for real, and returns a TrustedHTML object wrapping the transformed result, "HELLO WORLD".
  5. That object — not a string — is accepted by innerHTML, and the transformed text is what actually renders.
  6. A raw string, assigned elsewhere on the same page, is rejected exactly as in Module 15 — having a policy defined doesn't loosen the requirement for code that doesn't use it.

04 — The Code, Explained

The policy, with an observable rule — server.js:

const policy = trustedTypes.createPolicy('module16-demo', {
  createHTML: (input) => {
    ruleInvocationCount++;
    return input.toUpperCase(); // trivial, OBSERVABLE transform
  },
});

The finding we only caught by calling, not just checking typeof:

typeof policy.createScript  // "function" — even though no rule was given!
policy.createScript('1+1'); // THROWS:
// "Policy module16-demo's TrustedTypePolicyOptions did not specify a 'createScript' member."

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Intercept LEGACY code that still assigns raw strings — every call site has to explicitly opt into a policy (Module 17 changes this)
  • Restrict WHICH policy names are allowed to be created (Module 20)
  • Build a policy that actually removes dangerous content — ours just uppercases, a stand-in for a real transform

✓ CAN DO

  • Create a named, callable policy whose rule function genuinely executes on every call
  • Produce values a guarded sink will accept, verified by both type checks AND real rendered output
  • Confirm raw strings remain rejected everywhere a policy wasn't explicitly used — no accidental global loosening

07 — Brain Exercise

Think it through before revealing

Why does a TrustedTypePolicy object expose ALL THREE creator methods (createHTML, createScript, createScriptURL) as real, callable functions, instead of just omitting the ones you didn't provide a rule for — which would have made typeof policy.createScript report "undefined" and let you check for the omission with a simple if?

Reveal the answer:

Consider what code calling `policy.createScript(...)` actually needs to happen if the policy author never anticipated that call: a clear, immediate, unambiguous failure — not a silent `undefined` that then causes a confusing "X is not a function" error somewhere else, or worse, gets accidentally treated as if it succeeded. By always exposing the method and having it throw a SPECIFIC, NAMED error ("Policy X did not specify a createScript member") when the rule doesn't exist, the platform guarantees every misuse fails loudly, with a message that names the exact policy and the exact missing capability — much easier to debug than a generic `undefined is not a function`, and impossible to accidentally treat as a successful, silent no-op.

08 — There Are No Dumb Questions

Q: Does `String(trustedValue)` mean `TrustedHTML` secretly IS a string underneath?

No — and this matters for Module 22. `String(x)` calls `x`'s `toString()` method and returns a genuine, ordinary string built from whatever that returns; it doesn't reveal or unwrap some internal string `TrustedHTML` is "really" made of. We verified `trustedValue instanceof String` is `false` — a real, different type, that happens to have a `toString()` method, same as countless other JS objects.

Q: Could two different policies both be named `'module16-demo'`?

Not tested in this module (kept out of scope on purpose) — but per spec, calling `createPolicy` twice with the same name throws, UNLESS the `trusted-types` CSP directive explicitly allows duplicates via `'allow-duplicates'`. Module 20 covers policy-name restrictions in depth.

Q: Is `ruleInvocationCount` a Trusted-Types-specific mechanism?

No — it's just an ordinary JS closure variable we added ourselves, incremented inside our own rule function. Trusted Types doesn't provide any built-in "was my rule called" introspection; we built this purely to make Proof B's claim verifiable rather than assumed.
