01 — The Big Analogy

Imagine a building that just installed a new mail-scanning checkpoint, but most of the mail room staff have no idea it exists — they keep dropping envelopes in the same old chute they always have. Rather than retraining every employee, the building installs ONE special chute, labeled "default", that automatically routes anything dropped into ANY of the old, familiar chutes through the new scanner anyway — no retraining required, no employee needs to know the scanner was added. That one, specially-named chute is doing something no other named chute does: it catches traffic that was never addressed to it in the first place.

02 — What Happens, Step by Step

  1. Page creates a policy with the EXACT name "default", defining a createHTML rule that prepends a visible marker.
  2. Separately, "legacy" code — code that never references trustedTypes or any policy at all — assigns a raw string directly to innerHTML.
  3. Instead of throwing (Module 15's behavior), the assignment succeeds — and the rendered content shows the marker, proving the "default" policy's rule actually ran.
  4. Separately, the same legacy code calls eval('1+1'). The "default" policy never defined a createScript rule — this still throws, identically to having no default policy at all.

04 — The Code, Explained

The one name that changes everything — server.js:

trustedTypes.createPolicy('default', {
  createHTML: (input) => '[DEFAULT POLICY SANITIZED]: ' + input,
  // deliberately NOT defining createScript on this policy
});

// elsewhere, completely unmodified "legacy" code:
document.getElementById('legacy-target').innerHTML = 'a raw string...';
// ^ this line is IDENTICAL on both routes — what differs is only
//   whether a policy named "default" happens to exist

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Assume `"default"` covers every sink type just because it exists — it only auto-covers what it actually implements
  • Have TWO policies both named `"default"` (untested here, but per spec this is exactly as restricted as any duplicate name — Module 20's territory)
  • Choose which specific legacy call sites get auto-routed — it's ALL of them, or none

✓ CAN DO

  • Adopt Trusted Types incrementally in a real, large, pre-existing codebase without rewriting every single sink assignment
  • Verify — not assume — that legacy code's raw strings really do get transformed by the named policy's real rule function
  • Correctly predict that any sink category the default policy doesn't implement stays exactly as locked-down as Module 15

07 — Brain Exercise

Think it through before revealing

A large team adopts Trusted Types by adding a permissive "default" policy whose createHTML rule just returns its input completely unchanged (no sanitization, no transformation at all) — purely to stop the `TypeError`s from breaking their existing app while they migrate call sites individually over time. Does this provide ANY real security benefit on day one?

Reveal the answer:

On its own, close to none — a `createHTML` rule that echoes its input verbatim re-creates exactly Module 14's original, unrestricted baseline for every legacy call site, just wrapped in an extra function call. The real value of this pattern is entirely about MIGRATION SEQUENCING, not immediate protection: it lets a team ship `require-trusted-types-for` without an instant, app-breaking outage, then progressively tighten the default policy's rule (add real sanitization) or migrate individual call sites to their OWN named policies with tighter, call-site-specific rules — shrinking what the permissive default has to cover over time. It's a legitimate, common real-world rollout strategy, but it's a staging step, not a finish line.

08 — There Are No Dumb Questions

Q: Can a page have both a `"default"` policy AND other named policies?

Yes — they're not mutually exclusive. Named policies (Module 16's pattern) are for code that deliberately opts in and calls `policy.createHTML(...)` explicitly; `"default"` is specifically for code that does neither. A real app commonly has both: tightly-scoped named policies for code that was deliberately migrated, and a `"default"` catching whatever wasn't yet.

Q: Does the default policy get invoked for values that ALREADY came from a different named policy?

No — this module didn't need to test that directly because it follows from Module 16's Proof C: a value that's already a real `TrustedHTML` object (produced by any policy) is already the type the sink wants. The default policy only ever gets consulted when the sink receives something that ISN'T already a Trusted Types object — i.e., a plain string.

Q: Is there a performance cost to having a "default" policy that most legacy code silently routes through?

Not tested or measured in this course, and not the point of this module — the interesting property here is correctness/coverage, not performance. A real production rollout would profile this like any other hot-path code, same as any function that runs on every legacy sink call.
