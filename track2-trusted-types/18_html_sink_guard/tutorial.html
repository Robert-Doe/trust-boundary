01 — The Big Analogy

A real passport check doesn't just glance at whether the photo looks like you and the paper is roughly the right shade of blue — it checks specific, hard-to-forge structural properties (the chip, the watermark, the issuing authority's own records). Something that merely LOOKS like a passport from across the room — same color, same rough shape, a printed photo — fails the moment anyone actually checks it properly. This module checks whether the Trusted Types "passport check" is the real, structural kind, or just a glance.

02 — What Happens, Step by Step

  1. A real policy produces a real TrustedHTML value (no content transform this time — the test is about type, not content).
  2. That same value is handed to three DIFFERENT HTML sinks: innerHTML (property), outerHTML (property), insertAdjacentHTML (method argument). All three accept it.
  3. A plain object with a toString() method that returns realistic-looking HTML is handed directly to innerHTML — never touched any policy.
  4. A genuine, boxed String object (via new String(...)) — a real, non-fake JS type, just not the RIGHT type — is handed to innerHTML the same way.
  5. Both are rejected, with byte-for-byte identical error text to what a plain string would produce.

04 — The Code, Explained

Three sinks, one value — server.js:

document.getElementById('target-a').innerHTML = policy.createHTML('...');
document.getElementById('target-b').outerHTML = policy.createHTML('...');
document.getElementById('target-c').insertAdjacentHTML('beforeend', policy.createHTML('...'));
// all three: SUCCEEDED

Two imitations, same rejection — server.js:

const fake = { toString: () => '<b>fake</b>' };
el.innerHTML = fake; // THREW — looks right when stringified, still rejected

const boxed = new String('<b>boxed</b>');
el.innerHTML = boxed; // THREW — a REAL String object, still not TrustedHTML

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Explain the EXACT mechanism the guard uses to distinguish a real TrustedHTML from an imitation — Module 22 opens that up
  • Protect script-type sinks (`eval`, `script.src`) — this module only covers the HTML family
  • Guard against a forgery attempt more sophisticated than simple duck-typing (Module 23)

✓ CAN DO

  • Trust that the guard is enforced consistently across the whole HTML sink family, verified across three real sinks
  • Rule out "looks like the right string" as a way to satisfy a guarded sink
  • Rule out "is some kind of String-related object" as sufficient — it has to be the SPECIFIC TrustedHTML type

If Proof C throws unexpectedly, double check the argument ORDER for `insertAdjacentHTML(position, html)` — the guarded value is the SECOND argument, not the first; a surprisingly common mistake when adapting existing `insertAdjacentHTML` call sites to pass a `TrustedHTML` value.

07 — Brain Exercise

Think it through before revealing

Proof D's fake object and Proof E's boxed `String` both failed with the EXACT SAME error text as a plain string would. Given that, what's the simplest possible mental model for what the guard is actually checking — in one sentence, without using the word "content"?

Reveal the answer:

"Is this value's actual type `TrustedHTML`?" — full stop, nothing more sophisticated. Not "can this be turned into a string," not "does this object have a `toString` method," not "is this some flavor of String" — just a direct type identity check, which is why every non-`TrustedHTML` value, however convincingly it resembles the right string, fails identically. Module 22 goes one level deeper and shows you exactly HOW the browser performs that type check — which turns out to connect directly back to the JS prototype chain from the prerequisites layer.

08 — There Are No Dumb Questions

Q: Why test a boxed `String` specifically — who would ever write `new String(...)` in real code?

Less common by hand, but a realistic byproduct of some libraries, some older code patterns, or values that pass through certain APIs that box primitives. The point isn't "this is a common bug" — it's "even a REAL, non-fake String-family object doesn't get any special treatment," which rules out an entire category of "maybe strings are special-cased somehow" assumptions in one test.

Q: Does `insertAdjacentHTML`'s guard behave differently because it's a method, not a property setter?

Not in terms of outcome — we verified it accepts a real `TrustedHTML` and (implicitly, following the same TypeError pattern as A/B) would reject a raw value the same way. The mechanism differs slightly under the hood (checking a specific argument position vs. a property assignment), but the guarantee is the same: no non-`TrustedHTML` value gets through, regardless of which sink shape delivers the check.

Q: If I wrote my OWN class with a `toString()` that returns safe HTML, could I make the guard treat it as trusted?

No — Proof D is exactly this scenario, generalized. No amount of clever `toString()` implementation changes the object's actual type, and the guard checks type, not stringified output. This is precisely why Trusted Types is a meaningfully different guarantee than "developer promises this is safe" — it's checked by the platform, not by convention.
