01 — The Big Analogy

Module 18 tested one family of checkpoints (HTML sinks) and found them uniformly rigorous. This module tests a SECOND family — the ones governing code execution rather than markup — and finds something messier and more honest than a tidy analogy: some checkpoints in this family (eval, script.src) are fully staffed and rigorous. One (the Function constructor) turns out to have no checkpoint infrastructure installed at all yet — it just refuses everyone, real credentials or not. And one more (script.text) has a checkpoint that correctly checks credentials, but sits at a door that, it turns out, doesn't actually lead anywhere on its own. Real systems have seams like this, and finding them by testing — not by assuming symmetry — is the entire point of this module.

02 — What Happens, Step by Step

  1. A policy defines both createScript and createScriptURL, each returning input unchanged (same no-transform convention as Module 18).
  2. eval(policy.createScript('40 + 2')) — a real TrustedScript — succeeds, returns 42.
  3. new Function(policy.createScript(...)) — the SAME kind of real, valid value — throws anyway. The browser's own console explains: the Function constructor doesn't accept Trusted Types values at all yet.
  4. script.src = policy.createScriptURL('/child.js') succeeds; child.js genuinely loads and executes.
  5. script.text = policy.createScript(...) — the assignment itself succeeds (no throw) — but the resulting script never actually runs, confirmed by checking a marker variable directly, both before and after connecting the element to the document.
  6. A duck-typed fake object handed to script.src, and a plain string handed to the same sink, both throw with identical error text — the guard here is exactly as rigorous as Module 18's HTML sinks.

04 — The Code, Explained

The surprise the browser told us about directly — server.js / real console output:

new Function(policy.createScript('return 40 + 2'))
// THREW: EvalError: Evaluating a string as JavaScript violates this
// document's Trusted Type assignment requirements.
//
// console.info: "The JavaScript Function constructor does not accept
// TrustedString arguments. See https://github.com/w3c/webappsec-trusted-types/
// wiki/Trusted-Types-for-function-constructor for more information."

The test we had to fix after it silently tested the wrong thing:

// FIRST DRAFT (wrong): eval({ toString: () => '40 + 2' })
// → "succeeded", returning the object itself — because eval() only ever
//   evaluates STRING arguments; a non-string just passes through
//   unevaluated. Nothing to do with Trusted Types at all.
//
// FIXED: test the fake against script.src instead, which we'd already
// confirmed properly type-checks:
s.src = { toString: () => '/child.js' };  // THREW, correctly

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Use the `Function` constructor AT ALL once `require-trusted-types-for` is active — real code relying on it needs a different pattern entirely
  • Assume every sink in a "family" behaves like its most-tested member — verified false in this exact module
  • Rely on `.text` assignment alone to get a dynamically-created script to run

✓ CAN DO

  • Use `eval` and `script.src` with real Trusted Types values, fully guarded and fully functional
  • Correctly warn a team relying on `new Function(...)` that Trusted Types adoption will break it outright, not just restrict it
  • Recognize when a "failure" is actually a separate, general DOM-mechanics question rather than a Trusted Types finding

07 — Brain Exercise

Think it through before revealing

A teammate says: "Since `script.text` accepted our `TrustedScript` value without throwing, Trusted Types must be broken for that sink — the guard passed something dangerous through without actually protecting us." Is that the right read of what this module found?

Reveal the answer:

No — and separating the two facts (assignment succeeded; execution didn't happen) is exactly why this matters. The guard did its job completely correctly: it verified the value was a real, policy-produced `TrustedScript` and let it through — that's ALL Trusted Types ever promises for this sink. Whether the resulting script element then executes is governed by an entirely separate part of the HTML specification (the "prepare the script element" algorithm), which predates Trusted Types and applies identically whether Trusted Types exists or not. Conflating "the guard let it through" with "therefore something bad could happen" would be a real category error — the guard's job was narrowly and successfully accomplished; a DIFFERENT, unrelated browser mechanism is why nothing ran.

08 — There Are No Dumb Questions

Q: If `Function()` doesn't support Trusted Types, does that mean code using it is completely unprotected under `require-trusted-types-for`?

The opposite, in a sense — it's MORE restricted, not less: `new Function(anything)` throws unconditionally once the directive is active, whether the argument is a dangerous raw string, a harmless raw string, or a perfectly valid `TrustedScript`. Code relying on the `Function` constructor simply can't run at all under this policy; it has no working path, safe or unsafe. That's arguably the safest possible outcome for an unsupported sink, just not a usable one.

Q: Why does `eval()` behave so differently from `Function()`, given they're both "evaluate a string as code"?

Historically and specification-wise, they're different mechanisms with different integration timelines into the Trusted Types spec — `eval`'s Trusted Types integration shipped and is enforced; `Function`'s (per the browser's own cited tracking issue) has not yet reached the same state in this engine. This is exactly the kind of platform-maturity gap you can only find by testing directly, not by assuming two similar-sounding APIs behave identically.

Q: Could a REAL app work around the `Function()` gap?

Not explored in this module (out of scope for a course focused on verified behavior, not workaround engineering) — but the realistic answer for a real team is to avoid `new Function(...)` entirely under a Trusted-Types policy and use `eval` (properly policy-gated) or, more commonly, avoid dynamic code generation altogether in favor of static, reviewed functions.
