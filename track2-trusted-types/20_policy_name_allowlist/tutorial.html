00 — Prerequisites

You should already know: Module 16: Policy Factory Module 3: Directive Enforcement

01 — The Big Analogy

Modules 16-19 assumed a trustworthy team writing every policy on the page. But a real page often loads third-party scripts — an ad script, an analytics snippet, a widget — that run with the SAME privileges as your own code. Without a name allowlist, any of them could call trustedTypes.createPolicy('anything-they-want', { createHTML: (s) => s }) — a policy that just echoes input unchanged, silently recreating Module 14's original unrestricted baseline. The trusted-types CSP directive is a guest list at the door: only names YOU pre-approved get let in as policies at all, no matter who's asking.

02 — What Happens, Step by Step

  1. Server sends trusted-types approved-policy alongside require-trusted-types-for 'script'.
  2. trustedTypes.createPolicy('approved-policy', {...}) — a name on the list — succeeds.
  3. trustedTypes.createPolicy('rogue-policy', {...}) — a name NOT on the list — throws immediately, with a specific "disallowed" error naming the rejected policy.
  4. Attempting to create 'approved-policy' a SECOND time throws too, but with different text — an "already exists" error, a completely separate rule from the allowlist check.
  5. On a second route, the directive adds 'allow-duplicates' — now the second 'approved-policy' creation succeeds, while the still-disallowed 'rogue-policy' attempt fails identically to before.

04 — The Code, Explained

Two different real errors for two different rules — server.js / real console output:

trustedTypes.createPolicy('rogue-policy', {...});
// THREW: Policy "rogue-policy" disallowed.

trustedTypes.createPolicy('approved-policy', {...}); // 2nd time, no 'allow-duplicates'
// THREW: Policy with name "approved-policy" already exists.

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Let a third-party script define its OWN policy under a name you didn't pre-approve
  • Use wildcard or pattern-based name matching — the directive only supports an exact list
  • Redefine an already-created policy's behavior later, unless `'allow-duplicates'` is explicitly present

✓ CAN DO

  • Restrict policy creation to an explicit, developer-controlled allowlist of names
  • Distinguish "name never allowed" from "name already claimed" as two independently-enforced rules
  • Opt into relaxed uniqueness (`'allow-duplicates'`) without also opening up the name allowlist itself

07 — Brain Exercise

Think it through before revealing

Why does `'allow-duplicates'` exist at all — under what real circumstance would a team WANT to permit the same policy name to be defined more than once, given that Module 16 already showed each `createPolicy` call executes a specific, deliberate rule function?

Reveal the answer:

The most realistic case is hot-reloading or repeated script execution during development, or a module/bundle that might legitimately be evaluated more than once in complex loading scenarios (e.g., loaded via two different `<script>` tags by accident, or a testing environment that re-runs setup code). Without `'allow-duplicates'`, a second, accidental `createPolicy` call with the same name is a hard error — which is exactly the RIGHT default for production (an unexpected second definition of a trusted policy's rules is worth treating as suspicious), but can be legitimately relaxed in contexts where re-execution is expected and harmless.

08 — There Are No Dumb Questions

Q: Does `trusted-types` restrict the RULES a policy can define, or only its NAME?

Only the name — this module verified nothing about what `createHTML`/`createScript`/`createScriptURL` are allowed to DO. A policy named `'approved-policy'` with a rule that returns its input completely unchanged (no sanitization at all) is just as "approved" by this directive as one with careful sanitization. The allowlist controls WHO can define a policy under a given name, not WHAT that policy is allowed to do.

Q: Is `'none'` a real value for this directive?

Yes, per spec — `trusted-types 'none'` blocks policy creation entirely (no name would ever be accepted), which we didn't test directly in this module but follows the same "explicit allowlist, nothing implicit" pattern as everything else this directive does.

Q: Could a third-party script just... not call `createPolicy` and instead try to reuse an ALREADY-created policy object?

Only if it can reach a reference to that object — `createPolicy`'s return value is an ordinary JS object, and if your own code stores it on something globally reachable (like `window.myPolicy`), any script sharing that page's execution context could use it. This module's allowlist protects policy CREATION specifically; protecting an already-created policy object from misuse is a separate, ordinary JS-scoping concern, not something `trusted-types` addresses.
