01 — The Big Analogy

Module 10 built one black-box flight recorder for the whole aircraft. This module checks whether a completely different kind of incident — not "wrong heading" (a CSP script-src block) but "unauthorized crew member tried to enter the cockpit" (a blocked Trusted Types sink assignment or policy creation) — gets logged by that SAME recorder, or whether it needs its own separate black box nobody remembered to install. Good news, verified directly: one recorder, every incident type, no separate system required.

02 — What Happens, Step by Step

  1. A page wires up both reporting channels Module 10 verified: a `securitypolicyviolation` DOM listener and a `ReportingObserver`.
  2. Trigger 1: a raw string is assigned to `innerHTML` with no policy covering it — throws a `TypeError`, exactly like Module 15.
  3. Trigger 2: `createPolicy('rogue-policy', ...)` is attempted with a disallowed name — throws a `TypeError`, exactly like Module 20.
  4. BOTH triggers, independently, ALSO produce a real `securitypolicyviolation` event and a real `ReportingObserver` report — the thrown exception and the reporting signal are two separate, both-real things happening together.
  5. The two triggers produce different `blockedURI` values — `"trusted-types-sink"` vs. `"trusted-types-policy"` — making them distinguishable in a report stream.

04 — The Code, Explained

  domEvents.push({ blockedURI: e.blockedURI, violatedDirective: e.violatedDirective, sample: e.sample });

ro.observe();

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Guarantee network DELIVERY of these reports to a server — Module 10's same caveat applies identically here
  • Get a report for a sink assignment that SUCCEEDED via a valid policy — only failures are reported, same as ordinary CSP
  • Distinguish which SPECIFIC line of application code triggered a report without also reading `sourceFile`/`lineNumber` from the full report body

✓ CAN DO

  • Monitor Trusted Types adoption in production using the exact same infrastructure already built for CSP violations
  • Distinguish sink-assignment failures from policy-creation failures using `blockedURI`/`effectiveDirective` alone
  • Get an immediate, reliable LOCAL signal via `ReportingObserver`, independent of network delivery timing

07 — Brain Exercise

Think it through before revealing

A team already has a CSP violation dashboard built from Module 10's patterns. They adopt `require-trusted-types-for` and `trusted-types` for the first time. Do they need to build any new reporting infrastructure to start seeing Trusted Types failures on that same dashboard?

Reveal the answer:

No — and that's this module's whole finding, verified rather than assumed. Trusted Types violations flow through the identical `securitypolicyviolation`/Reporting API pipeline as ordinary CSP violations. Any existing collector endpoint, `ReportingObserver` hookup, or dashboard built for Track 1's violations will start receiving Trusted Types violations automatically the moment the new directives are added — distinguishable from other violation types by `blockedURI`/ `effectiveDirective`, but requiring zero new plumbing to arrive at all.

08 — There Are No Dumb Questions

Q: Does the `sample` field behave the same way it did in Track 1?

Yes and no — same field, richer content. Track 1's Module 5 found `sample` empty by default (requires `'report-sample'`). Here, both triggers show real, non-empty sample text — for the sink trigger, `"Element innerHTML|a raw string, no policy"` (identifying the sink AND showing the actual value); for the policy trigger, the attempted policy name itself, `"rogue-policy"`. Worth independently verifying whether `'report-sample'` was needed for these specific Trusted Types report types, or whether they include more detail by default — this module didn't test that distinction directly.

Q: Would a successful, policy-authorized sink assignment ALSO generate a report, just a "success" one?

No — same as every other violation-reporting mechanism this course has covered, only FAILURES generate reports. A successful `policy.createHTML(...)` call followed by an accepted `innerHTML` assignment produces no event, no report, nothing — reporting exists to surface problems, not to log routine, correct usage.

Q: Is `effectiveDirective: "trusted-types"` a real CSP directive name, same as `script-src`?

Yes — `trusted-types` (Module 20) and `require-trusted-types-for` (Module 15) are both genuine CSP directive names, which is exactly why their violations fit naturally into CSP's existing violation-reporting shape: from the reporting pipeline's perspective, a Trusted Types failure is just a violation of a CSP directive like any other, even though the underlying JS-level enforcement mechanism (throwing `TypeError`s from sink setters) is quite different from a blocked network request.
