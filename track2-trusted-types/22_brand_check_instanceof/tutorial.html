01 — The Big Analogy

Recall the prerequisites layer's wristband analogy: instanceof only checks whether a specific chain of links leads to a specific known object — it's a paperwork check, not a physical one. A forged employee ID badge can have the exact right barcode format, the exact right printed logo, even be laminated with the exact right hologram sticker if you know where to buy one — paperwork checks (matching an expected pattern) can be reproduced. What can't be reproduced without the real, physical manufacturing process is something like an embedded RFID chip that a badge reader queries directly — no visual inspection or paperwork trick recreates the actual chip. This module found exactly that distinction, for real: instanceof is the paperwork check (spoofable, and we proved it), and the sink's actual guard is the RFID reader (unspoofable, and we proved that too).

02 — What Happens, Step by Step

  1. A real policy produces a real TrustedHTML value. It passes instanceof TrustedHTML, and its prototype is confirmed to literally be TrustedHTML.prototype.
  2. A forged object is built with Object.create(TrustedHTML.prototype) — the exact construction the prerequisites page warned about — giving it the identical prototype link, with zero involvement from any policy.
  3. forged instanceof TrustedHTML is checked: true. The JS-level check is successfully spoofed.
  4. The forged object is handed to innerHTML anyway. It throws — but with a DIFFERENT error than every prior rejection in this course: "Illegal invocation", not "This document requires 'TrustedHTML' assignment."
  5. Every own property of the real value is inspected and copied onto an even-more-elaborate forgery. There's nothing to copy — a real TrustedHTML has zero own enumerable properties. The elaborate forgery is rejected identically anyway.
  6. The forged rejection is checked against Module 21's violation-reporting pipeline: no event fires. It's a different kind of failure entirely.

07 — Brain Exercise

Think it through before revealing

Module 18 already showed a duck-typed object ({ toString: () => '...' }) gets rejected by the sink. This module's forged object goes further — it even has the CORRECT prototype, passing `instanceof`. Why did we bother building the more sophisticated forgery, if the simpler one already failed?

Reveal the answer:

Because the simple duck-typed object failing proves less than it might seem to. A plain `{ toString: ... }` object fails `instanceof TrustedHTML` too — so Module 18 couldn't tell you WHICH check rejected it: could have been the type check, could have been the prototype check, could have been something else. This module deliberately built a forgery that passes the prototype check specifically, so that if the sink accepted it, we'd have learned the sink really does rely on `instanceof`-equivalent logic — and if it still rejected it (which is what we found), we've isolated something much stronger: the guard survives even when the ONE check `instanceof` performs is satisfied. That's a categorically stronger claim than Module 18 alone could support.

08 — There Are No Dumb Questions

Q: If `instanceof` can be fooled, is it ever meaningful to check `x instanceof TrustedHTML` in real code?

Yes, for ordinary, non-adversarial purposes — like checking a value's type before deciding how to log it, or for a lint rule flagging obviously-wrong usage. What this module shows is narrower and sharper: `instanceof` is not SECURITY-meaningful — it can't be trusted to gate a dangerous operation, because it can be satisfied by an object that never went through any policy at all. The browser's own sink implementation makes exactly that distinction, which is why it doesn't rely on `instanceof` either.

Q: Why does a real `TrustedHTML` have ZERO own properties — where does the actual HTML string live?

In an internal slot — a piece of state the spec defines as existing on the object, but which is not exposed as an ordinary, enumerable, copyable JS property. `String(trustedValue)` (Module 16) can read it out via a specific, defined `toString()` behavior, but `Object.keys()`, `Object.getOwnPropertyNames()`, spreading the object, or `JSON.stringify()` all see nothing, because none of those mechanisms have access to internal slots — only specific, spec-defined operations do.

Q: Does "Illegal invocation" mean the same thing everywhere you might see it in a browser?

It's a generic message browsers use for "this native method/property was invoked with the wrong kind of receiver" — the same text can appear for entirely unrelated mistakes, like calling `Array.prototype.push.call({}, 1)` incorrectly on certain engines, or detaching a method from its object (`const f = element.getBoundingClientRect; f()`). Seeing this exact text elsewhere doesn't necessarily mean Trusted Types is involved — context matters, which is why this module cross-checked it against the OTHER, TT-specific error message from prior modules rather than relying on the string alone.
