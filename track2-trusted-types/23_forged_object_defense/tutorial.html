01 — The Big Analogy

Module 22 tested one lock-pick. A thorough locksmith doesn't stop at "the first pick I tried didn't work" — they try picks that approach the lock from every different angle: tampering with the whole building's master-key system (prototype pollution), swapping the sign on the locksmith's own shop (reassigning the global constructor), trying a completely different picking tool (a different JS API for the same end state), and finally just photographing a real key and printing a copy (stealing the content). This module runs all four, so that "prototype tricks can't forge Trusted Types" becomes a conclusion backed by four independent, real experiments — not one experiment plus an assumption that it generalizes.

02 — What Happens, Step by Step

  1. Attack A: Object.prototype.polluted = 'yes' — confirmed to genuinely affect every plain object. A plain {} is still rejected by the sink, with the SAME error a totally un-forged string gets — pollution never even gets it as far as passing instanceof.
  2. Attack B: window.TrustedHTML — the global identifier itself — is reassigned to a fake constructor. This succeeds with no error at all (it's just a variable). An instance of the fake constructor is still rejected. The ORIGINAL real value, created before the reassignment, is tried again AFTER it — and still works.
  3. Attack C: the same prototype-linking result as Module 22, achieved via Object.setPrototypeOf instead of Object.create — identical outcome (passes instanceof, fails the sink with "Illegal invocation").
  4. Attack D: a real value's string content is extracted via String(real) and handed to the sink as a plain string — rejected, same as any other plain string.

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Test cross-realm forgery (an object created in a different iframe/window) — a different, spec-relevant scenario this module didn't cover
  • Point to the exact spec algorithm name for the internal-slot check — this course verified BEHAVIOR, not implementation source
  • Claim this defends against every conceivable attack — only the four specific, prototype-and-content-based ones tested here

✓ CAN DO

  • State, with four independent pieces of real evidence, that prototype-chain manipulation cannot forge a Trusted Types value
  • Explain specifically WHY: the sink's check is bound to internal state, not to the mutable global identifier, not to the forging method, not to content alone
  • Answer "how does Trusted Types relate to prototypal inheritance" concretely: it deliberately does NOT rely on it for its security guarantee, precisely because prototypal inheritance is attacker-manipulable and internal slots aren't

07 — Brain Exercise

Think it through before revealing

Across Modules 22 and 23, every single forgery attempt operated entirely within ordinary JavaScript — no browser bugs, no exploits, just standard, well-documented prototype and object APIs, used exactly as the language allows. Given that, in one sentence: why does Trusted Types work at all, if JavaScript itself puts no fundamental limits on what you can do to an object's prototype or a global variable's binding?

Reveal the answer:

Because the guarantee doesn't live in JavaScript-observable state at all — it lives in an internal slot that the ECMAScript/WebIDL object model defines as existing, but deliberately does not expose to any JS-level introspection or mutation mechanism. Every attack in these two modules manipulated something JS code CAN see and touch (a prototype link, a global identifier, an object's own properties, a string's content) — and every one failed because none of those things IS the internal slot. The security boundary isn't "JavaScript can't do certain things" (it can do a lot) — it's "the specific state that matters was never made reachable FROM JavaScript in the first place," which is a fundamentally different and much stronger kind of protection than relying on convention or obscurity.

08 — There Are No Dumb Questions

Q: Does this mean prototype pollution is never a real security concern in JavaScript generally?

No — prototype pollution is a real, well-documented class of vulnerability for OTHER kinds of code, particularly logic that trusts `instanceof` checks, uses objects as maps without `Object.create(null)`, or has conditional logic keyed on property presence (`if (obj.isAdmin)` where pollution could inject `isAdmin` onto every object). This module shows specifically that Trusted Types' OWN guarantee is immune to it — not that pollution is harmless everywhere.

Q: If `window.TrustedHTML` can be reassigned freely, is there any way to protect it, like `Object.freeze(window)`?

Not tested in this module, and beside the point this module makes: the sink's actual security guarantee doesn't depend on `window.TrustedHTML` being unmodifiable — Attack B's whole finding is that reassigning it changes nothing about the sink's behavior either way. Freezing it might be reasonable defensive hardening for OTHER reasons (preventing confusion, preventing other code from relying on a tampered reference), but it isn't what makes Trusted Types itself secure.

Q: Could an attacker with the ability to run arbitrary JS on the page do real damage some OTHER way, even with Trusted Types fully enforced?

Yes, almost certainly — Trusted Types protects specific DOM-XSS sinks; it says nothing about, for example, reading `document.cookie`, making arbitrary `fetch()` calls, or manipulating the DOM through APIs it doesn't guard. Trusted Types' scope is narrow and precise: it closes the sink-injection gap Module 14 identified, and this module confirms that specific guarantee resists prototype-based forgery. It was never meant to be a general "attacker JS can't do anything" boundary.
