01 — The Big Analogy

Every module before this one built and tested one piece of the checkpoint system in isolation — the badge format, the ID scanner, the forgery detector. This module opens the doors for a real day of traffic: a real security guard (DOMPurify, an actual, independently-maintained library, not a toy we wrote), checking a real stream of visitors that includes known troublemakers in eight different disguises, alongside ordinary legitimate guests carrying perfectly normal luggage (real rich-text content). The measure of success isn't "did the checkpoint exist" — it's "did every troublemaker get stopped, and did every legitimate guest get through unbothered."

02 — What Happens, Step by Step

  1. A real, unmodified DOMPurify 3.4.13 build (vendored via npm, not a CDN) loads as a same-origin script.
  2. A policy named dompurify-policy is created, whose createHTML rule calls DOMPurify.sanitize() on its input and returns the result.
  3. Eight real XSS payload shapes — a script tag, an onerror handler, an onload handler, a javascript: URL in an anchor, one in an iframe, a <body onload> fragment, a CSS url(javascript:...), and an attribute-breakout attempt — are each run through policy.createHTML() and assigned to innerHTML.
  4. A global marker, set only if any payload's embedded code actually runs, is checked after all eight: it stayed false.
  5. Separately, real legitimate rich-text HTML (bold, italic, a real link, a list) is run through the exact same policy — and comes out byte-for-byte identical to what went in.

04 — The Code, Explained

The one policy backing every proof — server.js:

const policy = trustedTypes.createPolicy('dompurify-policy', {
  createHTML: (input) => DOMPurify.sanitize(input, { RETURN_TRUSTED_TYPE: false }),
});

05 — Limits / What You Cannot Do Yet

✗ CAN'T DO YET

  • Claim DOMPurify neutralizes every conceivable payload shape — this corpus is eight real examples, not an exhaustive security audit
  • Assume a sanitizer is defending a vector that's actually just obsolete in modern browsers (the CSS payload's real lesson)
  • Skip the `require-trusted-types-for` awareness even in your OWN trusted UI-building code — it guards everything, no exceptions

✓ CAN DO

  • Ship the complete, real pattern: a real sanitizer, wrapped in an explicit, named, auditable Trusted Types policy
  • Verify — not assume — that legitimate content survives sanitization unchanged
  • Correctly integrate a real third-party library's own internal Trusted Types usage alongside your own policy

07 — Brain Exercise

Think it through before revealing

This module found that DOMPurify left the CSS url(javascript:...) payload completely unchanged, yet the overall result was still "0/8 executed." A teammate argues: "That proves DOMPurify handles it correctly after all — the marker stayed false." Is that the right conclusion?

Reveal the answer:

No — and this is worth being precise about, the same way DECISIONS.md is. The marker stayed false because MODERN BROWSERS no longer execute `javascript:` URLs referenced from CSS `url()` — a defense that has nothing to do with DOMPurify at all. If a browser (or a future CSS feature) ever revived that capability, this exact payload would sail through completely unsanitized, because DOMPurify's default configuration didn't touch it. The correct, precise claim is: "this specific payload shape is currently harmless due to an unrelated browser-level protection, not because our sanitizer defended against it" — conflating the two would leave a real, latent gap invisible until the browser-level protection changed for some other reason.

08 — There Are No Dumb Questions

Q: Why does DOMPurify need its OWN internal Trusted Types policy at all — why can't it just use the one WE create?

DOMPurify's sanitization process itself needs to build a DOM tree from the dirty input internally (to walk and filter it) — that internal DOM-building uses guarded sinks too, and DOMPurify has no way to know or reach into whatever policy YOUR calling code happens to have created. It solves this by creating its own, separately-named policy for its own internal use, which is exactly why that name needs its own allowlist entry.

Q: Does this module prove Trusted Types + DOMPurify makes an application fully immune to XSS?

No, and this course has been careful not to claim that. It closes the specific gap Module 14 identified (sinks accepting raw strings unconditionally) for the sinks Trusted Types actually guards. Track 1's CSP modules cover a different, complementary set of protections. Neither layer — nor both together — claims to be a complete security solution against every possible vulnerability class; they're real, verified, specific defenses against real, specific attack shapes.

Q: If we'd used `DOMPurify.sanitize(input)` directly (letting IT return a TrustedHTML, instead of wrapping it in our own policy), would anything have worked differently?

Functionally, likely similar results for these specific payloads — but the AUDITABILITY would differ. Our own explicit `dompurify-policy` is a single, visible, developer-authored point where "raw string becomes trusted" happens, matching this course's pattern since Module 16. Relying entirely on DOMPurify's own internal policy would make that same trust decision invisible to code review at the call site — a real, if subtle, engineering tradeoff between the two integration styles.
